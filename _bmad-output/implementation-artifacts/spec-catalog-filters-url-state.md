## Intent

**Problem:** В каталоге `(blue)/catalog` в URL живут только `search`, `page`, бейджи и категория, пришедшая по внешней ссылке. Цена, сортировка, «в наличии», мультивыбор брендов и категория, выбранная кликом в сайдбаре, живут только в React-состоянии, поэтому F5, возврат «назад» из карточки товара и открытие ссылки в новой вкладке сбрасывают их к умолчаниям.

**Approach:** Зеркалить оставшиеся фильтры в query-параметрах тем же паттерном, что уже применён к `page`: состояние — источник истины для запроса, URL — его зеркало. Ленивая инициализация состояния из URL, sync-эффект для «назад»/«вперёд», запись в URL из обработчиков одним вызовом `updateSearchParams`.

## Boundaries & Constraints

**Always:**
- Контракт URL: `category` — slug; `brand` — CSV из slug'ов (одиночный slug из `BrandsBlock` остаётся валидным); `ordering` — одно из пяти значений `<select>`; `min_price`/`max_price` — целые; `in_stock` — только `false`.
- Значения по умолчанию в URL **не пишутся** и вычищаются из пришедшей извне ссылки одним `replace` (как уже сделано для `page=1`): `ordering=name`, `in_stock=true`, `min_price=1`, `max_price=50000`, пустой `brand`.
- Смена любого фильтра по-прежнему сбрасывает `page` и вызывает `fetchProducts` **ровно один раз**.
- Мусор в параметре трактуется как значение по умолчанию, страница не падает и ошибку не показывает.
- **Разбор цены — одно правило на оба конца:** значение, не являющееся целым числом в
  `[PRICE_MIN, PRICE_MAX]` (`1`…`50000`), заменяется умолчанием **своего** конца (`min` → `1`,
  `max` → `50000`); если после разбора `min > max`, оба конца берут умолчания (не swap, не подтягивание
  одного конца к другому). **Clamp запрещён:** бэкенд отрицательное значение и так игнорирует
  (`backend/apps/products/filters.py:281,307`), а зажатие `max_price=-5` к `1` дало бы пользователю
  пустую выдачу вместо всего каталога. Правило идемпотентно — канонизация не зациклится.
- `min_price`/`max_price` фильтруют по **видимой роли цене**: `filter_min_price`/`filter_max_price`
  (`backend/apps/products/filters.py:272-315`) считают границу по `opt1/opt2/opt3` для B2B и по
  `retail_price` для гостя и розницы. Одна и та же ссылка `?min_price=…` даёт **разную выдачу**
  гостю и опт-клиенту — это единственный роле-зависимый параметр в наборе. Поведение намеренное
  (AC5 стори `security-wholesale-price-visibility`: иначе выдача расходится с ценой в карточке),
  дефектом не считается и в этой правке не меняется.
- `router.push(..., { scroll: false })` для действий пользователя, `router.replace` — только для канонизации URL; no-op при неизменной query-строке сохраняется.
- Существующая защита от устаревшего ответа (`requestSeq`) обязана покрывать новые параметры, включая внешнюю навигацию «назад»/«вперёд».

**Ask First:**
- Вынос в URL `viewMode` (сетка/список) и `expandedKeys` (раскрытые ветки дерева) — это состояние UI, не фильтр выдачи.
- Любое изменение backend-контракта фильтров товаров.

**Never:**
- Не трогать `(electric)/electric/catalog`, страницу поиска, `components/ui/Pagination`, `SearchPageClient`.
- Не хранить фильтры в `localStorage`/`sessionStorage`.
- Не чинить предсуществующий дефект «внешнее удаление `search` не очищает поисковое состояние» (запись в `deferred-work.md`) — он вне объёма.
- Не менять `brand` на CSV из **id**: URL остаётся человекочитаемым и совместимым со старыми ссылками.

- **Эффект дерева категорий зависит от `categorySlugParam`** (549). Как только клик по категории
  начнёт менять URL, эффект заново вызовет `getTree()` и выполнит `setExpandedKeys(new Set(...))` —
  replace, не merge, — то есть схлопнет раскрытые ветки на каждом выборе категории.
- **Состояние брендов — `Set<number>` (id), URL — slug'и.** Отображение возможно только после
  загрузки `brands` (эффект 560–585). Без гейта первый запрос уйдёт без бренда, а второй — с ним:
  лишний запрос и мигание выдачи на закладке `/catalog?brand=nike`.
- **Инвалидация `requestSeq` на commit** (777) завязана на `productFilters`, а при внешней навигации
  в первом render состояние ещё прежнее — ровно то окно, ради которого заведён отдельный
  layout-эффект по `[pageParam, page]` (682). Для новых параметров окно то же самое.
- `frontend/src/app/(blue)/catalog/__tests__/CatalogPage.test.tsx` (1137 строк) — честный роутер-мок
  уже есть и включается opt-in: `enableRouterNavigation()` в `beforeEach`, `restoreRouterMocks()` в

- `frontend/src/services/productsService.ts:154` — `ProductFilters`; поля `brand`, `min_price`,

- `frontend/src/app/(blue)/catalog/layout.tsx:7` — canonical жёстко `/catalog`, поэтому новые

**Acceptance Criteria:**
- Given применены цена, сортировка, снятое «в наличии», два бренда и категория из сайдбара,
  when пользователь обновляет браузер, then все фильтры и выдача восстанавливаются без мигания
  дефолтного состояния.
- Given ссылка `/catalog?category=obuv&brand=nike,adidas&ordering=-created_at&page=2`,
  when её открывают в новой вкладке, then применяются все четыре параметра и запрос уходит один раз.
- Given любая смена фильтра — включая «в наличии», категорию и «назад»/«вперёд», when она
  обработана, then `productsService.getAll` вызывается ровно один раз, а `categoriesService.getTree`
  за всё время жизни страницы вызывается ровно один раз.
- Given любое расхождение URL с состоянием, when оно приводит к бампу `requestSeq`, then за ним
  следует запрос товаров: скелетон загрузки не остаётся на экране ни в одном сценарии матрицы.
- Given `npm run lint`, `npx tsc --noEmit` и `npm run test` после правки, when они запускаются,

## Design Notes

Почему состояние, а не производное от URL: `router.push` в App Router обновляет `searchParams`
асинхронно (transition). При производном значении смена фильтра дала бы промежуточный рендер
«новый фильтр + старая страница» и второй лишний запрос. Обоснование целиком — в
`spec-catalog-pagination-url-state.md`, раздел Design Notes; здесь тот же механизм тиражируется.

Единый источник для трёх мест (инициализация, sync, канонизация) — один мемо распарсенных
параметров, а не три независимых разбора:

```ts
const urlFilters = useMemo(() => ({
  ordering: parseOrdering(orderingParam),
  price: parsePriceRange(minPriceParam, maxPriceParam),
  inStock: parseInStock(inStockParam),
  brandSlugs: parseBrandSlugs(brandSlugParam),
}), [orderingParam, minPriceParam, maxPriceParam, inStockParam, brandSlugParam]);
```

Канонизация обязана быть идемпотентной: `serialize(parse(url)) === serialize(parse(serialize(parse(url))))`,
иначе `replace` зациклится. Защиту даёт no-op-гард в `updateSearchParams`, но полагаться только на
него нельзя — парсеры должны возвращать канонические значения сами.

   no-op-гард сравнивает по-прежнему закодированные строки, поэтому его поведение не изменилось.

3. **Расхождение с базовой линией тестов.** Полный набор до правки не замерялся; после правки —

   на каждый шаг, поэтому введено второе состояние `priceDraft` (только UI), а `priceRange` остался
   источником истины для запроса и URL и принимает драфт одним шагом через `PRICE_COMMIT_DELAY_MS`

**Наблюдение по ползунку цены (предсуществующее, вне объёма):** проп `step` в `PriceRangeSlider`
используется только для расчёта минимального зазора между концами, но на сам `<input type="range">`
атрибут `step` не ставится. Поэтому клавишами и перетаскиванием цена меняется шагом 1, а не
`PRICE_STEP=500` (в живой проверке 10 нажатий дали `min_price=11`). На debounce и зеркалирование в URL
не влияет, спекой не затрагивается.

**Наблюдение по окружению (не дефект правки):** стек был поднят без сервисов `db` и `redis` —
backend падал в `could not translate host name "db"`, nginx отдавал 502. Подняты `db`/`redis`,
перезапущены `backend` и следом `nginx` (иначе upstream остаётся недоступным).

**Наблюдение по контракту цены (предсуществующее, вне объёма):** `?min_price=1&max_price=50000`
даёт `count=3501`, а запрос вовсе без этих параметров — `9237`: бэкенд отсекает товары без видимой
роли цены. Значения `1`/`50000` — умолчания *слайдера*, а не «фильтр выключен», и `productFilters`
слал их и до правки (`page.tsx`, `min_price`/`max_price` без условия). Канонизация убирает их
только из URL, состав запроса не меняется, поэтому выдача та же. Если когда-нибудь потребуется
«без фильтра цены» — это отдельное продуктовое решение.
