# Интент: `UnmarkedTestWarning` как гейт при явном `-m`

> Бриф для исполнения в чистом контекстном окне. Составлен 2026-08-14 по факту проверки кода;
> все пути, номера строк и числа сверены с рабочим деревом на коммите `23ca9203`.
> Это интент, а не спека: `status`-фронтматтера намеренно нет.

## Задача

Хук авторазметки маркеров в `backend/conftest.py` при встрече теста, которому маркер проставить нечем, выдаёт `warnings.warn(..., UnmarkedTestWarning)`. Предупреждение **не влияет на код возврата**, тонет в общей сводке рядом с `RemovedInDjango60Warning` и в CI-логе на несколько тысяч строк прочитано не будет. За ту же по сути ошибку внутри `backend/` хук рвёт сбор `pytest.UsageError`, а снаружи — шепчет.

**Решение уже принято (Alex, 2026-08-13) — переигрывать не нужно:** хук поднимает `UsageError` вместо предупреждения, **когда среди аргументов pytest есть явный `-m`**. Без `-m` поведение остаётся прежним (предупреждение).

### Почему именно так

Тихое выпадение теста вредит ровно тогда, когда идёт отбор по маркеру: тест без маркера при `-m unit` молча не попадает ни в один прогон. При полном прогоне без `-m` он исполняется, и терять сбор не за что.

Отвергнутые альтернативы (не предлагать заново):

| Вариант | Почему нет |
|---|---|
| `filterwarnings = error::conftest.UnmarkedTestWarning` в обоих `pytest.ini` | Ломает и локальный прогон, и чужой сбор — ту самую асимметрию, которую сохранили намеренно. Плюс хрупкий резолв категории: `conftest` — не уникальное имя модуля |
| `-W error::conftest.UnmarkedTestWarning` в CI-вызовах | Дублируется в четырёх workflow, забудется на пятом; не защищает от `--disable-warnings` |
| Отдельный CI-шаг с `grep -q UnmarkedTestWarning` | Требует `tee` лога, переживает не всякий формат вывода |

**Побочная выгода выбранного варианта:** `UsageError` не глушится ни `-p no:warnings`, ни `--disable-warnings`. Вторая половина находки ревью («предупреждение можно заглушить флагом») закрывается тем же изменением, отдельной работы не требует.

## Главная ловушка — прочитать до написания кода

**Все 13 вызовов хука в тестах передают `config=None`:**

```python
root_conftest.pytest_collection_modifyitems(None, [item])
```

Сейчас хук аргумент `config` не использует вовсе, поэтому `None` проходит. Реализация, читающая `config.option.markexpr` в лоб, уронит 13 существующих тестов с `AttributeError: 'NoneType' object has no attribute 'option'`.

Два выхода, оба приемлемы:

1. **Защитный доступ** — `getattr(getattr(config, "option", None), "markexpr", "")`. Диф меньше, существующие тесты продолжают работать и означают «`-m` не задан» → режим предупреждения. **Цена:** сломанный или неожиданный `config` молча деградирует гейт до предупреждения — то есть отказ в сторону тишины у механизма, который эту тишину и чинит. Если выбираешь этот путь, назови компромисс в комментарии.
2. **Обновить все 13 вызовов**, передавая подставной config. Честнее по семантике, но правит больше строк в тесте.

## Кто это увидит в CI

Все четыре прогона используют явный `-m`, то есть ужесточение включится в CI автоматически, без правки workflow:

- `.github/workflows/backend-ci.yml:209` — `-m "not integration and not data_dependent and not performance and not slow"`
- `.github/workflows/main.yml:139` — `-m "not performance and not slow"`
- `.github/workflows/deploy.yml:116-118` — тот же фильтр, что в `backend-ci` (`-m` на строке-продолжении, `grep 'pytest .*-m'` его не находит)
- `.github/workflows/performance-tests.yml:126` — `-m "performance or slow"`

**Ни один workflow править не требуется.** Если возникает желание что-то в них поменять — это сигнал, что реализация пошла не туда.

## Границы

**Не трогать:**

- `pytest.UsageError` для непокрытых путей **внутри** `backend/` (`conftest.py:189`) — существующий сторож, к задаче отношения не имеет.
- Асимметрию «внутри рвём сбор, снаружи мягче» как принцип — она осознанная. Меняется только то, при каких условиях «снаружи» тоже становится жёстким.
- Workflow-файлы (см. выше).

**Известное ограничение, которое эта задача не закрывает и не должна:** предупреждение (а после правки — и ошибка) появляется только там, где `backend/conftest.py` вообще загружен, то есть когда rootdir равен `backend/` либо среди аргументов есть хотя бы один путь внутри него. Вызов `pytest /tmp/ext/test_x.py` без единого внутреннего пути даёт другой rootdir, conftest не подхватывается, и ни одна наша строка не исполняется. Закрыть это из conftest невозможно в принципе — требуется плагин, установленный в окружение (entry point или `-p`). Ограничение уже задокументировано в шапке `backend/conftest.py:15-19`.

## Что проверить

Тесты гоняются только в Docker с PostgreSQL. Файл `test_pytest_marker_autotagging.py` вызывает хук напрямую, без Django и без реального сбора, поэтому отрабатывает за доли секунды.

```bash
cd docker && docker compose -p freesport-test -f docker-compose.test.yml run --rm -T backend \
  pytest -v backend/tests/unit/test_pytest_marker_autotagging.py
```

Путь внутри контейнера — от `/app`, то есть `tests/unit/test_pytest_marker_autotagging.py`. `--env-file` не передавать: файла `docker/.env` нет, и подстановок в `docker-compose.test.yml` тоже. После прогона — `down`.

**Новые тесты обязаны покрыть обе стороны развилки:** при заданном `-m` — `UsageError`; без `-m` — по-прежнему `UnmarkedTestWarning` и продолжение сбора. Второй случай важнее: именно он удерживает намеренную асимметрию, и именно его легко потерять.

Полный прогон для проверки, что ужесточение не сломало существующий набор:

```bash
cd docker && docker compose -p freesport-test -f docker-compose.test.yml run --rm -T backend pytest -v -m unit
```

Это заодно и есть боевая проверка: команда содержит явный `-m`, то есть исполняется в новом, жёстком режиме.
