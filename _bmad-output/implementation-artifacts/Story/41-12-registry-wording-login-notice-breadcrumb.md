## Story

As a оператор персональных данных,
I want чтобы регистрационный номер, ссылка на политику при входе и служебные подписи интерфейса читались однозначно и по-русски,
so that регулятор и посетитель находили нужные сведения без толкования сокращений.

**Закрывает:** FR-41-15 (ссылка в подвале), FR-41-17a/17b (уточнение — полная формулировка номера), FR-41-17c (номер во всех трёх подвалах), FR-41-24 (редакция 3 обоснования), FR-41-27 (строка о политике при входе), FR-41-28 (русская подпись цепочки); находка create-story 41.10 — открытый редирект после входа (решение Alex 2026-09-11, расширение объёма эпика принято осознанно, прецедент стори 41.4).

**Каноническая формулировка (дословно, везде одинаковая):**
`Регистрационный номер в реестре операторов, осуществляющих обработку персональных данных`
Сокращение «ПДн» в отображаемом тексте недопустимо — сканер 10.09.2026 его не распознал (гипотеза H1, SCP п. 4.4). Уточнение «(Роскомнадзор)» на витрине не добавляем: каноническая фраза фиксируется один раз и проверяется тестами посимвольно. Номер оператора — `26-22-003980` (ИП Семерюк Д.В.); номер лицензиара `26-22-004188` остаётся только на `/requisites`.

## Acceptance Criteria

### AC1 (FR-41-17a/17b) — `/requisites` с полной формулировкой

**Given** страница `/requisites`
**When** она отображается
**Then** обе строки с номером подписаны канонической формулировкой «Регистрационный номер в реестре операторов, осуществляющих обработку персональных данных»
**And** значения не изменились: `26-22-004188` у «Владелец сайта» (ИП Терещенко), `26-22-003980` у «Пользователь сайта» (ИП Семерюк); номера не переставлены и не продублированы
**And** порядок строк в обоих блоках и вёрстка на ширине 375px не изменились

### AC2 (FR-41-17c) — номер оператора во всех трёх подвалах

**Given** подвалы — общий `Footer`, `ElectricFooter` и собственный подвал `/coming-soon`
**When** они отображаются
**Then** в каждом есть строка с номером оператора **26-22-003980** в канонической формулировке (например: «Регистрационный номер в реестре операторов, осуществляющих обработку персональных данных: 26-22-003980»)
**And** номера **26-22-004188** ни в одном из подвалов нет
**And** строка — обычный текст, не ссылка

### AC3 (FR-41-15, решение Alex 2026-09-10) — ссылка на возврат в общем подвале

**Given** общий подвал (`Footer.tsx`)
**When** он отображается
**Then** в блоке «Клиентам» есть ссылка «Условия возврата и рекламаций», ведущая на `/partners#returns`
**And** ссылки «Возврат» в блоке «Информация» нет — ссылка на `/partners#returns` в общем подвале остаётся ровно одна
**And** прочие ссылки и их порядок не меняются; особая раскладка «Контакты внутри „Компания“» (`isDefaultLayout`) сохраняется

### AC4 (FR-41-27) — строка о политике на форме входа

**Given** форма входа на любом варианте адреса `/login` (в т.ч. `/login?next=…`)
**When** она отображается
**Then** под кнопкой «Войти» — строка «Входя, вы подтверждаете, что ознакомлены с „Политикой обработки персональных данных“», где название политики — ссылка на `/privacy-policy`
**And** это информирование, а не согласие: чекбокса нет; строка не входит в реестр версий текстов согласий (`consent_texts.json`, `CONSENT_TEXT_VERSIONS` не меняются) и не пишется в журнал `UserConsent`; слова «соглашаетесь» в тексте нет

### AC5 — открытый редирект после входа закрыт

**Given** адрес входа с параметром `next` или `redirect`, указывающим за пределы сайта (`https://…`, `//…`, `/\…`, `javascript:…`)
**When** пользователь успешно входит или открывает `/login`, уже будучи авторизованным
**Then** переход выполняется на `/`, а не по параметру: `LoginForm` проверяет адрес через `isSafeRedirectUrl` перед `router.push`, а `isSafeRedirectUrl` отвергает и вариант с обратным слэшем (`/\evil.com` по WHATWG разбирается в `https://evil.com/` — см. Dev Notes)
**And** внутренний адрес (`/checkout`, `/profile`) по-прежнему открывается после входа — `/login?next=%2Fcheckout` из стори 41.10 работает
**And** оба случая закреплены тестами: опасные значения → `/`, безопасные внутренние пути → по параметру

### AC6 (FR-41-28) — русская подпись навигационной цепочки

**Given** навигационные цепочки — общая `Breadcrumb`, `ElectricBreadcrumbs` и `ProductBreadcrumbs` в карточке товара
**When** проверяется разметка
**Then** `aria-label` равен «Навигационная цепочка», латинских подписей `aria-label="Breadcrumb"` в исходниках `frontend/src` не осталось
**And** тесты ищут элемент по новой подписи

### AC7 (FR-41-24, редакция 3) — обоснование по форме входа

**Given** стори 41.10 влита (выполнено — PR #158)

**And** п. 4 опирается на реализованное FR-41-25 (гость на `/checkout` получает приглашение войти, формы сбора ПДн ему недоступна), строка FR-41-27 описана как информирование, а не согласие
**And** редакцию 3 утверждает владелец до того, как её предъявят регулятору — в story-файле фиксируется, кем и когда утверждена

Меняется только вызываемая из middleware `isSafeRedirectUrl`.
- Не реализует перенос гостевой корзины при входе — `merge_guest_cart_on_login` мёртв, дефект отложен (`deferred-work.md`, раздел «Deferred from: create-story 41.10…»).
- Не добавляет чекбокс, поле формы или запись в журнал согласий на `/login` (FR-41-27 — только информирующий текст).
- Не правит текст политики в коде и не меняет `Page`/CMS — п. 1.2 правится через админку (AC8).
- Не чинит предсуществующий дефект контраста `text-muted`-ссылок `ElectricFooter` (вынесен в deferred-work стори 41.1) — но и **не копирует** его на новую строку номера (см. Task 2.2).
- Не трогает `RegisterForm`/`B2BRegisterForm`/`register/page.tsx`/`login/page.tsx` напрямую — они получают укрепление бесплатно через общий `isSafeRedirectUrl` (Task 5); регресс их поведения проверяется прогоном, а не правками.
- Не меняет тексты согласий, `consentTexts.ts`, `consent_texts.json`, `openapi.yaml`, типы API — backend-контракт не затронут.
