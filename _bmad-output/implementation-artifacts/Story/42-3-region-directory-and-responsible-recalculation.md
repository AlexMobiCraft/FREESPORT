# Story 42.3: Справочник регионов и разовый пересчёт ответственных

Status: review
Baseline Revision: 02298949

## Story

As a руководитель отдела продаж,
I want видеть регионы по названиям, знать, какие из них не распределены, и одной командой назначить ответственных всем уже существующим клиентам,
so that после запуска у каждого клиента был менеджер, а не только у зарегистрированных позже.

**Закрывает:** FR-42-06, FR-42-09. **Источник:** `_bmad-output/planning-artifacts/epic-42-staff-admin-sections.md` (Story 42.3), спецификация `_bmad-output/specs/spec-staff-admin-sections/` (CAP-2, Assumptions, Success signal).

**Предусловие — стори 42.2 слита в `develop`** (на `02298949` она в статусе ready-for-dev, кода ещё нет). Эта стори вызывает её символы:
- `staff_accounts_q()` в `apps/users/staff_roles.py`;
- `region_key`, `resolve_responsible`, `resolve_responsible_for_key`, `ResponsibleResolution`, `SOURCE_*` в `apps/users/services/responsible_manager.py`;
- поля `User.responsible_manager` и `User.responsible_manager_manual`;
- поле `ManagerRoutingRule.manager`.

Ветку `feature/42-3-region-directory-recalculation` создавать от `develop` после мёрджа 42.2. Прежде чем писать код, прочитать Completion Notes 42.2: при расхождении имён или сигнатур с перечисленными выше править эту стори по факту, а не 42.2.

**Чего в этой стори нет:**
- таблицы регионов в разделе руководителя `/supervisor/` и блока «Не распределены» там — это 42.7. Здесь справочник и список нераспределённых — функции, которые 42.7 переиспользует, плюс их вывод в `/admin/` суперпользователя, чтобы владелец распределил регионы на точке выката;
- ручного и массового переназначения, записей `AuditLog` — 42.7;
- автоназначения по событиям и пересчёта при смене правила — это 42.2, здесь они не меняются.

## Утверждённые решения (не пересматривать)

1. **Справочник — статический словарь в коде, не таблица БД.** Названия субъектов меняются раз в годы, правка — через PR. Модуль `backend/apps/common/regions.py`, рядом с `ManagerRoutingRule`: его читают и `common/admin.py`, и сервисы `users`. Модуль не импортирует ничего из `apps.users`.
2. **Состав справочника — 97 кодов** (полный текст — Dev Notes, «Справочник»):
   - 01–79 — субъекты РФ;
   - 83, 86, 87, 89 — автономные округа;
   - 80, 81, 82, 84, 85, 88 — бывшие автономные округа. Субъектов больше нет, но ИНН при укрупнении не меняется: на проде есть клиенты с 80, 81, 85;
   - 90–95 — Запорожская обл., Крым, Севастополь, ДНР, ЛНР, Херсонская обл.;
   - **97 — г. Москва, ИНН выданы после 2014 г.** Диапазон 77 закончился, и московские инспекции выдают новым организациям ИНН с 97. На проде **83 клиента** с ИНН на 97, правила на этот код нет — сегодня они уходят на резерв, а не к менеджеру Москвы;
   - 99 — «Крупнейшие налогоплательщики» (формулировка эпика).

   96 и 98 в справочник не входят: регионам они не соответствуют, на проде клиентов с ними нет. Такой код показывается как есть (AC1).
3. **«Не распределён» = нет активного правила `inn_region` с назначенным `manager`.** Правило, у которого есть только `manager_email`, ответственного не даёт (42.2, решение 3). Клиенты такого региона уходят на резерв, поэтому для руководителя регион всё ещё не распределён (эпик, Additional Requirements: «правила без учётной записи выводятся руководителю как требующие назначения»). Правила по стране и резервные на список не влияют: в нём только коды справочника.
4. **Пересчёт — management-команда `recalculate_responsible_managers`, не миграция.** Её запускают вручную на проде после распределения регионов (action item эпика 42). Логику назначения команда не дублирует: разрешение берёт из `resolve_responsible_for_key` (42.2), с кэшем по ключу региона.
5. **Команда не обнуляет ответственного.** Если нет активного резервного правила с `manager`, обычный запуск завершается `CommandError` до любых изменений. `--dry-run` в той же ситуации печатает отчёт с предупреждением. Это защищает 4600 записей от массового сброса из-за забытого резерва.
6. **Команда пишет через `QuerySet.update()`.** `User.save()` не вызывается: его хук автоназначения здесь не нужен, а `updated_at` (`auto_now`) не трогается, чтобы 4600 записей не выглядели изменёнными. Выгрузок клиентов по `updated_at` нет (grep на `02298949`), так что это не ломает обмен — это решение о чистоте данных. `UPDATE` повторяет условие `responsible_manager_manual=False`: ручное назначение, сделанное во время прогона, не затирается.
7. **Записей `AuditLog` команда не пишет.** Лента 42.9 показывает только действия сотрудников, служебные операции в неё не попадают. Итог прогона — в `logger.info`.

## Acceptance Criteria

### AC1 — справочник регионов

**Given** справочник `apps/common/regions.py`
**When** запрашивается `region_name(code)` для кода 01–99
**Then** для каждого из 97 кодов справочника, включая 90–95 и 97, возвращается название, для 99 — «Крупнейшие налогоплательщики»
**And** код вне справочника («96», «00», «7», «ab») возвращается как есть, без ошибки; `None` и пустая строка — пустая строка
**And** каждый код из сида правил `common/0018` есть в справочнике

### AC2 — список нераспределённых

**Given** активные правила `inn_region` с `manager` покрывают часть кодов
**When** вызывается `unassigned_regions()`
**Then** возвращаются ровно коды справочника без активного правила `inn_region` с `manager`, по возрастанию кода, с названиями
**And** код с активным правилом без `manager` (только `manager_email`) и код только с неактивным правилом в списке есть
**And** правила по стране и резервные на список не влияют
**And** когда все 97 кодов покрыты, список пуст
**And** функция делает один SQL-запрос

### AC3 — названия и нераспределённые в `/admin/`

**Given** суперпользователь открывает список правил маршрутизации в `/admin/`
**When** страница отрисована
**Then** у правил `inn_region` есть колонка «Регион» с названием субъекта (у правил по стране — страна, у резервных — «—»)
**And** над списком блок «Не распределены (N): 80 — …, 97 — …» либо «Все регионы распределены»
**And** число SQL-запросов страницы не растёт с числом правил

### AC4 — пересчёт назначает ответственных

**Given** клиенты:
- без ответственного;
- с ответственным по правилу;
- с ответственным, не совпадающим с правилом;
- с ручным назначением;
- с ролью `unregistered`;
- без ИНН;
- учётные записи сотрудников с ИНН региона (`is_staff`, суперпользователь, `role="admin"`, член каждой из трёх групп)

**When** запускается `python manage.py recalculate_responsible_managers`
**Then** у каждого клиента без ручного назначения `responsible_manager == resolve_responsible(country, tax_id).manager`: по правилу региона или страны, без ИНН — по резервному
**And** ручные назначения и учётные записи сотрудников не тронуты
**And** `updated_at` клиентов не изменился

### AC5 — отчёт и идемпотентность

**Given** команда пересчёта завершилась
**When** выводится отчёт
**Then** в нём числа: проверено клиентов, назначено по коду региона, назначено по стране, ушло на резервное правило, пропущено из-за ручного назначения, без изменений, и их сумма равна числу проверенных
**And** перечислены коды справочника без менеджера, клиенты которых ушли на резерв, с названием и числом клиентов
**And** повторный запуск без изменений в правилах даёт 0 во всех трёх строках «назначено», а «без изменений» равно числу проверенных минус ручные

### AC6 — `--dry-run`

**Given** режим `--dry-run`
**When** запускается команда
**Then** выводится тот же отчёт, что дал бы обычный запуск, с пометкой «пробный запуск»
**And** в базе ничего не меняется (ни одного `UPDATE "users"`)

### AC7 — защита от пустого резерва

**Given** нет активного резервного правила с `manager`
**When** запускается команда без `--dry-run`
**Then** она завершается `CommandError` с объяснением на русском, ни один клиент не изменён
**And** с `--dry-run` печатается отчёт со строкой «Без ответственного (нет резервного правила с менеджером): N» и предупреждением

### AC8 — производительность

**Given** 5 и 50 клиентов в одних и тех же трёх регионах
**When** запускается команда
**Then** число SQL-запросов в обоих случаях одинаковое: оно зависит от числа различных ключей регионов, а не от числа клиентов (NFR-42-04)

### AC9 — регрессия и проверки

**Given** итоговая ветка
**When** в Docker выполняются полный backend-прогон, `flake8`, `black --check`, `mypy`, `makemigrations --check` и `check_openapi_sync`
**Then** всё зелёное, ожидания существующих тестов не изменены, миграций нет, API не изменился
