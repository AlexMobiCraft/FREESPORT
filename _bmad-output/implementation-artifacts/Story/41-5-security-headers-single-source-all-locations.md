# Story 41.5: Единый источник заголовков безопасности и их доставка во все локации

Status: in-progress

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

> 🟠 **Вторая стори эпика 41, закрывает дефект с ограниченным путём эксплуатации.** `/media/` отдаётся **без** `X-Content-Type-Options: nosniff`. Кто туда пишет — проверено по коду: девять полей загрузки в `backend/apps/` (баннеры, бренды, иконки и изображения категорий, галерея товара), **все админские; публичной загрузки файлов на сайте нет**. Второй источник — изображения из обмена 1С (`import_files/`): они приходят из внешней системы без человека в цикле, и это единственный путь, не требующий входа в админку. Файл, принятый оттуда, может быть распознан браузером как HTML и исполнен в origin сайта.
> 🟡 **Срочности нет** (решение владельца 2026-08-25). Путь эксплуатации требует либо доступа в админку, либо контроля над выгрузкой 1С; поломка `mail.optisport.ru` из-за `includeSubDomains` не задевает никого — веб-почтой не пользуются. Стори делается сейчас не потому, что горит, а потому что контекст свежий и потому что это **дешёвая репетиция выката** перед 41.3: первый выкат после того, как выяснилось, что падение фронта на проде маскируется заглушкой со статусом 200 (Dev Notes → «Порядок применения правок»). Аудит дефекта не увидел — он проверял только `/coming-soon`, где заголовки на месте, и поставил блоку «Техническая защита» 98/100.
> 🟢 **Свежесть координат: проверено чтением файлов на коммите `460b3b6f`** (эпик писался на `db125f82`; все строки из его текста подтверждены, ни одна не съехала).
> 🟢 **Blast radius LOW по графу вызовов.** `npx gitnexus impact "Method:frontend/next.config.ts:headers#0" --direction upstream` → `risk: LOW`, `impactedCount: 0`. `npx gitnexus context nextConfig` → `incoming: {}`, `outgoing: {}`. Граф здесь бесполезен: правки идут в **конфигурации** (nginx, `next.config.ts`, Django settings), которые GitNexus как символы не связывает. Реальный риск — в трафике: набор заголовков стоит на **каждом** ответе сайта.
> ⚠️ **Новый каталог `docker/nginx/snippets/` не попадёт в контейнер сам.** nginx монтируется **пофайлово** (`docker-compose.yml:141-142`, `docker-compose.prod.yml:163-164`), каталога `conf.d` целиком нет. Без нового `volumes`-пункта в **обоих** compose-файлах nginx упадёт на старте с `open() "/etc/nginx/snippets/..." failed`. И первый выкат требует **пересоздания контейнера** (`up -d nginx`), а не `nginx -s reload` — reload новый bind-mount не увидит.
> ⚠️ **`add_header` внутри `location` заменяет весь унаследованный набор, а не дополняет его.** Это причина FR-41-22 и главный источник регрессий в этой стори. Любая локация, которая объявляет свой `add_header`, обязана переобъявить набор целиком.

## Story

As a **администратор сайта**,
I want **чтобы каждый ответ нёс ровно один экземпляр каждого заголовка безопасности и чтобы заголовки доходили до всех отдаваемых ресурсов**,
so that **браузер применял политику предсказуемо, а пользовательские загрузки не могли быть исполнены как разметка**.

**Закрывает:** FR-41-06, FR-41-07, FR-41-08, FR-41-09, FR-41-10, FR-41-22, FR-41-23.

## Acceptance Criteria

**AC1 (FR-41-06).**
**Given** запрос к HTML фронтенда (`location /` → Next)
**When** проверяются заголовки ответа
**Then** `X-Frame-Options` и `Referrer-Policy` присутствуют ровно в одном экземпляре каждый
**And** их значения приходят из `frontend/next.config.ts`, а nginx на этой локации их не добавляет

**AC2 (FR-41-22).**
**Given** запрос к `/static/`, `/media/`, картинке товара (`/products/*.jpg`) или `/health`
**When** проверяются заголовки ответа
**Then** присутствуют `X-Content-Type-Options: nosniff` и остальной набор заголовков безопасности
**And** прежний `Cache-Control` этой локации сохранён без изменений (`/static/` — `public, immutable`; `/media/` и картинки товаров — `public`)
**And** заголовки приходят и на ответы, отличные от 200: `/media/1c_temp/…` (404), `/media/x.php` (403) — то есть `add_header` объявлен с флагом `always`

**AC3 (FR-41-07).**
**Given** любой ответ сайта по HTTPS, включая статику, медиа, `/api/`, `/admin/` и HTML
**When** проверяются заголовки
**Then** `Strict-Transport-Security` присутствует **ровно один раз** с явным `max-age`
**And** значение — ровно `max-age=31536000`: `preload` и `includeSubDomains` **не** добавляются. Проверка поддоменов выполнена при подготовке стори, решение принято, переоткрывать вопрос не нужно (см. Dev Notes → «HSTS»)
**And** Django перестаёт отдавать собственный HSTS — сейчас именно он шлёт на `/api/` и `/admin/` значение `max-age=31536000; includeSubDomains; preload`, запрещённое этим AC (`base.py:607-609`, `production.py:33-35`); после правки единственным источником остаётся nginx
**And** на проде подтверждено замером, что `includeSubDomains` из ответа ушёл — это снимает действующую поломку `http://mail.optisport.ru` в браузерах, успевших закэшировать старое значение

**AC4 (FR-41-08).**
**Given** любой HTML-ответ
**When** проверяется CSP
**Then** политика содержит директиву `frame-ancestors`
**And** её значение согласовано с `X-Frame-Options` **на той же поверхности**: HTML фронтенда и ресурсы, которые отдаёт сам nginx, получают `frame-ancestors 'self'` при `X-Frame-Options: SAMEORIGIN`; локации Django (`/api/`, `/admin/`, `/swagger/`, `/redoc/`) — `frame-ancestors 'none'` при `X-Frame-Options: DENY`. Рассогласование недопустимо: в поддерживающих браузерах `frame-ancestors` перекрывает `X-Frame-Options`, и пара «`SAMEORIGIN` + `'none'`» молча свела бы запас на нет (решение владельца 2026-08-25, см. Dev Notes → «Встраивание»)
**And** остальная часть политики **не** изменяется: `default-src 'self' http: https: data: blob: 'unsafe-inline'` остаётся как есть — ужесточение вынесено в `tech-debt.md` п. 23

**AC5 (FR-41-09).**
**Given** любой HTML-ответ и любой ответ, который отдаёт сам nginx
**When** проверяются заголовки
**Then** присутствует `Permissions-Policy`, запрещающий неиспользуемые возможности браузера
**And** в значении нет `interest-cohort` — директива снята из Chrome 115+ и даёт `Unrecognized feature` в консоли, что противоречит AC6

**AC6 (NFR-41-05).**
**Given** страница `/delivery` со встроенной картой Яндекса, страницы с изображениями товаров, оформление заказа и обмен с 1С
**When** заголовки изменены
**Then** карта на `/delivery` открывается, изображения грузятся, ошибок CSP в консоли браузера нет
**And** обмен с 1С (`/api/v1/integrations/1c/exchange/`) и загрузка файлов проходят без регрессий

**AC7 (FR-41-10).**
**Given** заголовок `Cache-Control` HTML-ответа статически пререндеренной страницы (эталон — `/coming-soon`)
**When** он проверяется
**Then** HTML не кэшируется на срок, сопоставимый с годом (`s-maxage=31536000` исчезает)
**And** правка выполнена в **стратегии генерации страницы** Next, а не в nginx и не в `headers()` — `Cache-Control`, заданный в `next.config.ts`, Next в production перезаписывает

**AC8 (FR-41-23).**
**Given** документация архитектуры
**When** стори завершена
**Then** `docs/architecture/11-security-performance.md` описывает выбранную границу ответственности, а не установку `X-Frame-Options` в рукописном Django-middleware (`XSSProtectionMiddleware`, строки 208-215)

**AC9 (доставка конфигурации).**
**Given** новый каталог сниппетов nginx
**When** поднимается окружение
**Then** каталог смонтирован в контейнер nginx в **обоих** compose-файлах — `docker/docker-compose.yml` (dev) и `docker/docker-compose.prod.yml` (prod)
**And** `docker compose exec nginx nginx -t` проходит без ошибок
**And** в Completion Notes зафиксировано, что первый выкат на прод требует `up -d nginx` (пересоздание контейнера), а не `nginx -s reload`

**AC10 (паритет dev).**
**Given** локальное окружение (dev-nginx поднят на `local.conf`)
**When** проверяются заголовки `/static/`, `/media/` и картинок товаров через `http://localhost/`
**Then** набор заголовков безопасности присутствует и там — без `Strict-Transport-Security`, потому что локально нет TLS
**And** локальный набор задан тем же сниппетом, что и прод, а не скопированным текстом

**AC11 (тесты-стражи).**
**Given** конфигурация после правки
**When** прогоняются тесты
**Then** существует тест, падающий при возврате дефекта: локация в `default.conf`/`local.conf` объявила свой `add_header`, но не подключила сниппет
**And** существует тест, фиксирующий состав `headers()` в `next.config.ts` (наличие CSP с `frame-ancestors`, `Permissions-Policy`, отсутствие `Cache-Control`)
**And** существует тест, фиксирующий, что Django не является вторым источником HSTS
**And** существует тест, фиксирующий наличие `X-XSS-Protection` во всех трёх сниппетах nginx и в `headers()` (AC12: единственный источник — nginx, и локация с собственным `add_header` теряет его молча)
**And** существует тест, фиксирующий монтирование каталога сниппетов в обоих compose-файлах

**AC12 (границы объёма).**
**Given** объём стори
**When** оценивается диапазон правок
**Then** **не** трогаются: содержание CSP помимо `frame-ancestors` (tech-debt п. 23), 2FA админки (tech-debt п. 22), логика приложения, сериализаторы и API-контракт (`docs/api/openapi.yaml` регенерации не требует), кэш и SEO-разметка страниц сверх правки `revalidate` из AC7
**And** `X-XSS-Protection: 1; mode=block` сохраняется **на всех поверхностях, где приходит сегодня**: HTML, `/static/`, `/media/`, картинки товаров, `/health`, `/api/`, `/admin/`, `/swagger/`, `/redoc/`. Заголовок устарел, но его удаление не входит в требования эпика и отдельно бы объяснялось перед регулятором
**And** источник у него ровно один, и это **не** Django: `SECURE_BROWSER_XSS_FILTER` в `base.py:604` и `production.py:31` — мёртвая настройка, Django перестал отдавать этот заголовок в 4.0 (в проекте 5.2.7), и замер прода это подтверждает — в списке заголовков от Django его нет. Сегодня он приходит **только** с серверного уровня nginx (`default.conf:89`). Значит любая локация, получившая собственный `add_header`, теряет его вместе со всем унаследованным набором и обязана переобъявить его явно: `app-headers.conf` — для Django-локаций, `security-headers*.conf` — для того, что отдаёт nginx, `next.config.ts` — для HTML
**And** формулировка этого AC уточнена 2026-08-25 (см. Change Log): исходная редакция говорила «сохраняется в текущем виде», не называя источник, и по ней план правок из Task 3.3/3.4 молча снёс бы заголовок с пяти поверхностей из шести

**AC13 (ручная проверка на живых контейнерах).**
**Given** пересобранное окружение
**When** снимаются заголовки со всех перечисленных локаций
**Then** результаты сведены в таблицу в Completion Notes: для каждой локации — полный список заголовков безопасности и число вхождений каждого
**And** ни один заголовок из набора не встречается дважды, и ни одна локация не осталась без `nosniff`
**And** запас на встраивание проверен положительно, а не только заявлен: страница сайта, открытая во фрейме на странице того же origin, отображается; страница `/admin/login/` в том же фрейме — нет

## Dev Notes

### Главный механизм: `add_header` заменяет, а не дополняет

В nginx директивы `add_header` наследуются с предыдущего уровня **только если на текущем уровне нет ни одной собственной**. Как только в `location` появляется хоть один `add_header`, весь унаследованный набор с уровня `server` пропадает. Именно поэтому четыре локации в `docker/nginx/conf.d/default.conf` — `/static/` (95-110), `/media/` (112-134), картинки товаров (139-144), `/health` (201-205) — теряют **все пять** серверных заголовков (88-92): у каждой есть свой `add_header Cache-Control` или `Content-Type`.

Отсюда два следствия для реализации:

1. Проверка «заголовок объявлен в конфиге» ничего не доказывает. Доказывает только снятый с живого ответа заголовок — поэтому AC13 требует таблицу замеров, а не diff.
2. Вложенные локации (`~* \.(css|js)$` внутри `/static/`, `/media/1c_temp/`, `~* \.(php|py|pl|sh)$` внутри `/media/`) собственных `add_header` не имеют и наследуют набор **родительской локации**. Достаточно починить родителя. Но `return 404` и `deny all` дают статусы вне списка «200/204/301/302/304», поэтому `always` обязателен.

### Эталонная схема сниппетов

**Три плоских файла, без вложенных `include`** (решение владельца 2026-08-25; прежняя редакция предлагала пять файлов с деревом включений — см. Change Log).

```
snippets/security-headers.conf         → Strict-Transport-Security
                                       + Permissions-Policy
                                       + CSP … frame-ancestors 'self'
                                       + X-Frame-Options SAMEORIGIN
                                       + X-Content-Type-Options nosniff
                                       + Referrer-Policy strict-origin-when-cross-origin
                                       + X-XSS-Protection 1; mode=block

snippets/security-headers-no-hsts.conf → то же самое БЕЗ Strict-Transport-Security
                                         (внутренний vhost, local.conf)

snippets/app-headers.conf              → Strict-Transport-Security
                                       + Permissions-Policy
                                       + CSP … frame-ancestors 'none'
                                       + X-XSS-Protection 1; mode=block
                                         (XFO / nosniff / Referrer-Policy ставит Django)
```

Почему плоско, а не деревом. Дерево включений (`hsts.conf` + `permissions-policy.conf`, вложенные в остальные) экономило одну-две дублированные строки и добавляло за это способ ошибиться: путь внутри `include`, разрешаемый в bind-mount'е, которого не существует, пока контейнер не пересоздан. Цена плоской схемы — три копии `Permissions-Policy` и три почти одинаковых CSP — оплачена стражем из Task 10.1, который сверяет их между собой. Цена дерева стражем не оплачивается.

Раздвоений в наборе ровно два, оба намеренные: `frame-ancestors` (`'self'` на сайте, `'none'` на Django-локациях, см. «Встраивание») и наличие HSTS (нет там, где нет TLS).

Раскладка по локациям HTTPS-vhost:

| Локация | Кто отдаёт ответ | Что подключается | Почему |
|---|---|---|---|
| уровень `server` | — | `security-headers.conf` | безопасный дефолт для всего, что не объявит своё |
| `/static/`, `/media/`, `/products/*.ext`, `/health` | nginx | `security-headers.conf` | у них есть свой `add_header` → наследование потеряно |
| `/coming-soon/`, `~ /\.`, `~ ~$` | nginx | ничего | своих `add_header` нет → наследуют серверный набор |
| `/` | Next | одиночный `add_header` HSTS | вытесняет серверный набор; остальное ставит `next.config.ts`, **включая `X-XSS-Protection`** |
| `/api/`, `/admin/`, `/swagger/`, `/redoc/` | Django | `app-headers.conf` | Django ставит XFO (`DENY`)/nosniff/Referrer сам; CSP, Permissions-Policy и `X-XSS-Protection` он не умеет |

Схема — рекомендация, а не буква AC. Отступать можно, но инвариант «каждая локация с собственным `add_header` переобъявляет набор целиком» обязан сохраниться, и тест из Task 10.1 его закрепляет.

Две вещи, которые легко сделать лишними и сломать этим ответ:

- **`add_header` не подавляет заголовки апстрима.** Заголовки, пришедшие от Next или Django, проходят через nginx всегда. Одиночный `add_header` HSTS в `location /` вытесняет только *нинксовый* унаследованный набор — набор от Next остаётся. `proxy_hide_header` для этого не нужен и не должен появляться: он, наоборот, срежет то, что стори обязана доставить.
- **Сниппеты нельзя класть в `conf.d/`.** `nginx.conf:96` подключает `include /etc/nginx/conf.d/*.conf` на уровне `http`, и файл со списком `add_header` был бы разобран как глобальная конфигурация вместо переиспользуемого фрагмента. Каталог — именно отдельный (`snippets/`), отсюда и новый mount из Task 5.

### Почему `/api/` и `/admin/` получают CSP от nginx, а не от Django

**Решение принято владельцем 2026-08-25, переоткрывать не нужно.**

Граница ответственности из эпика назначает `/api/` и `/admin/` Django и указывает `settings/production.py`. Буквально это невыполнимо: Django настройками умеет только `X_FRAME_OPTIONS`, `SECURE_CONTENT_TYPE_NOSNIFF`, `SECURE_REFERRER_POLICY`, `SECURE_HSTS_*` и `SECURE_CROSS_ORIGIN_OPENER_POLICY`. Ни CSP, ни `Permissions-Policy` настройки не покрывают. Замер прода это подтверждает: CSP на `/admin/login/` сегодня приходит **от nginx**, Django его не шлёт.

Рассмотренные альтернативы и почему отклонены:

- **`django-csp`** — покрывает только CSP; `Permissions-Policy` всё равно остался бы без источника. Новая прод-зависимость ради половины задачи.
- **Свой middleware в Django** (~20 строк) — закрыл бы оба заголовка и работал бы в деве на `localhost:8001`. Отклонён как преждевременный: в `backend/apps/` сейчас **ни одного** рукописного middleware, а выгода от «CSP видно в деве» сегодня нулевая — политика разрешает практически всё (`unsafe-inline`, `https:`), нарушить её нечем.

Взято: nginx добавляет `/api/`, `/admin/`, `/swagger/`, `/redoc/` **только те два заголовка, которых Django не ставит**. Дублирования не возникает, новых сущностей в бэкенде — тоже.

**Условие пересмотра, которое надо зафиксировать письменно (Task 9.3):** когда возьмутся за `tech-debt.md` п. 23 (ужесточение CSP через `Report-Only`), «где живёт CSP» станет содержательным вопросом — политика с nonce/хэшами должна формироваться приложением, а не статической строкой в конфиге. Тогда источник для Django-локаций переезжает в приложение. Это условие обязано попасть и в п. 23 tech-debt, и в `docs/architecture/11-security-performance.md`.

`SECURE_REFERRER_POLICY` в настройках не задан — Django 5.2 по умолчанию отдаёт `same-origin` (подтверждено замером). Это **отличается** от `strict-origin-when-cross-origin` на HTML. Расхождение допустимо (разные поверхности, оба значения строгие); если решишь унифицировать — задай `SECURE_REFERRER_POLICY` явно и отметь это в Completion Notes, но менять поведение молча нельзя.

Снято с `https://optisport.ru` — это baseline для сравнения в AC13. Каждая строка — то, что реально приходит клиенту.

Три вывода, которые надо держать в голове при реализации:

1. **`X-Frame-Options` и `Referrer-Policy` приходят парами с противоречивыми значениями** на всех трёх динамических поверхностях. Спецификация поведение при нескольких `X-Frame-Options` не определяет, браузеры склеивают их в невалидное `DENY, SAMEORIGIN` и разрешают это по-разному: защита от клик-джекинга сейчас в неопределённом состоянии. Это содержательная часть FR-41-06, а не гигиена.
2. **`includeSubDomains` уже на проде** и приходит от Django. То есть поломка веб-почты из Dev Notes → «HSTS» — не будущий риск, а действующее состояние: браузер, открывавший админку или API, уже не может зайти на `http://mail.optisport.ru`. Правка это чинит — новый заголовок без `includeSubDomains` перезапишет запись в браузере при первом же визите по HTTPS.
3. **Двойной `Cache-Control` на `/static/`** — `expires 1y` и `add_header` дают два заголовка; браузер берёт первый. Поведение не меняем (AC2 требует сохранить прежний `Cache-Control`), но при правке локации не «почини» это заодно — это отдельный вопрос вне объёма.

### HSTS: сейчас источников два, останется один

Django выставляет HSTS на `/api/` и `/admin/` (`production.py:33-35`, значения дублированы в `base.py:607-609`): `max-age=31536000; includeSubDomains; preload`. nginx не выставляет его нигде — поэтому HTML сайта сегодня идёт **без** HSTS, а `/api/` — с `preload`, который AC3 запрещает.

`preload` — не косметика: он означает заявку на включение домена в предзагруженный список браузеров, откуда выход занимает месяцы. Заголовок уже отдаётся, но пока домен не подан на hstspreload.org, эффекта нет; убрать его сейчас дёшево. Вдобавок `preload` без `includeSubDomains` невалиден, а последний по итогам проверки ниже не берётся.

**`includeSubDomains` не включается — решение принято, обоснование уточнено 2026-08-25.**

Причина не в том, что «сломается веб-почта»: владелец веб-почтой не пользуется, и её недоступность сама по себе никого не задевает. Причина — **асимметрия обратимости**. `includeSubDomains` записывается в браузер на год и не отзывается: сняв заголовок, ты лишь перестаёшь запись продлевать, а у всех, кто уже был на сайте, год продолжает идти, и кнопки «всё равно перейти» под HSTS нет. Отказ сегодня стоит одной строки и отменяется любым днём позже. Выгода при этом нулевая: единственный веб-поддомен — `www`, и он защищается собственным заголовком при первом же HTTPS-визите.

Разбор DNS-зоны reg.ru от 2026-08-25 и замеры TLS показывают, во что именно упёрлась бы запись, если бы её сделали:

| Поддомен | A | Что это | HTTPS |
|---|---|---|---|
| `optisport.ru` | 5.35.124.149 | наш сервер | Let's Encrypt, SAN `optisport.ru` + `www.optisport.ru`, до 07.11.2026 |
| `www` | 5.35.124.149 | наш сервер | покрыт тем же сертификатом |
| `mail`, `smtp`, `pop` | 31.31.197.15 | хостинг reg.ru | **блокер, см. ниже** |
| `ftp` | 5.35.124.149 (AAAA — reg.ru) | по IPv4 попадает на наш nginx | сертификат имя не покрывает |
| `billing-ping` | 127.0.0.1 | служебная запись reg.ru | — |

Блокер — веб-почта: `http://mail.optisport.ru/` отдаёт **200** и работает, а `https://mail.optisport.ru/` предъявляет сертификат `CN=*.hosting.reg.ru` (SAN только `*.hosting.reg.ru`) — имя не совпадает. С `includeSubDomains` браузер каждого, кто открывал `optisport.ru`, начал бы принудительно переписывать `http://mail…` в `https://`, упирался бы в невалидный сертификат и **не смог бы его обойти** — под HSTS кнопки «всё равно перейти» нет. Веб-почта стала бы недоступна из браузера на год.

`ftp.optisport.ru` в браузере сломан уже сегодня (наш же nginx редиректит его на HTTPS, а сертификат `ftp` не покрывает) — `includeSubDomains` тут ничего не меняет. Почтовые протоколы SMTP/IMAP/POP HSTS не применяют, они не затронуты в любом случае.

Потеря от отказа минимальна: `www` защитится собственным заголовком при первом визите по HTTPS, а других веб-поддоменов у домена нет. Вернуться к `includeSubDomains` можно, когда у `mail.optisport.ru` появится валидный сертификат.

Два наблюдения **вне объёма стори** (в код не идут, кандидаты в `tech-debt.md`): веб-почта работает по HTTP, то есть пароль от почты уходит открытым текстом; A-запись `ftp.optisport.ru` указывает на веб-сервер, где FTP нет.

### Почему кэш чинится не заголовком, а стратегией генерации

`Cache-Control: s-maxage=31536000` на статически пререндеренных страницах ставит Next, и попытка перебить его через `headers()` в `next.config.ts` не сработает: Next в production перезаписывает `Cache-Control`, заданный в конфиге ([Next.js docs — CDN Caching](https://nextjs.org/docs/app/guides/cdn-caching), [next.config.js headers](https://nextjs.org/docs/pages/api-reference/config/next-config-js/headers)). Значение управляется сегментной опцией `revalidate`: с `revalidate = N` ответ становится `s-maxage=N, stale-while-revalidate=…`.

`export const revalidate` допустим и в `layout.tsx`, и в `page.tsx`; для маршрута берётся наименьшее значение по дереву сегментов. Поэтому дефолт в корневом `frontend/src/app/layout.tsx` безопасен: `(blue)/home/page.tsx:16` (3600) и `(electric)/electric/page.tsx:38` (3600) уже совпадают, `app/page.tsx:15` с `export const dynamic = 'force-dynamic'` остаётся динамическим.

Конкретика по риску: `/coming-soon` — полностью статическая страница (`(coming-soon)/coming-soon/page.tsx`, три строки, ни одного `fetch`), именно её и сканировал аудит. После запуска сайта общий кэш может год отдавать заглушку. Обрати внимание на тонкость маршрутизации: `/coming-soon` уходит в Next через `location /`, а `/coming-soon/` (со слэшем) — на статический файл из `docker/nginx/coming-soon/`, который nginx отдаёт сам. Это две разные поверхности, и заголовки нужны обеим.

### Что на самом деле встроено в страницы (для AC6)

AC говорит про виджеты CDEK и Boxberry, но в коде их нет: `frontend/src/components/checkout/DeliveryOptionsPlaceholder.tsx` — заглушка со статическим списком, интеграции с API CDEK/Boxberry ещё не сделаны (стори 15.3 не реализована). Единственный реальный сторонний фрейм на сайте — **карта Яндекса** на `/delivery` (`(blue)/delivery/page.tsx:59-60`, `https://yandex.ru/map-widget/v1/...`). Её и надо проверять.

`frame-ancestors` на неё не влияет: директива ограничивает, **кто может встроить нас**, а не кого встраиваем мы. За встраивание отвечает `frame-src`, который сейчас откатывается к `default-src` с разрешённым `https:` — и остаётся нетронутым по AC4. Это конкретная причина, по которой CSP в этой стори ужесточать нельзя: любое сужение `default-src` сломает карту.

`Permissions-Policy` с `geolocation=()` карту не сломает — геолокация в кросс-origin iframe и так закрыта по умолчанию. Но если Task 11.2 покажет обратное, `geolocation` из списка убрать и отметить в Completion Notes.

### Встраивание: почему `SAMEORIGIN`, а не `DENY`

**Решение владельца 2026-08-25: оставить запас на встраивание внутри сайта.**

Контекст выбора. Сегодня `X-Frame-Options` приходит парой (`DENY` от приложения, `SAMEORIGIN` от nginx), спецификация поведение при нескольких значениях не определяет, и браузеры разрешают конфликт по-разному. Куда бы ни склонился выбор, конфликт устраняется — вопрос был только в том, какое значение оставить.

Проверенная фактура на момент решения: единственный iframe в коде — карта Яндекса на `/delivery` (мы встраиваем чужое, к делу не относится); rich-text редакторов в админке нет; полей загрузки файлов девять и все админские (`banners/models.py:85,94`; `common/models.py:684,784`; `products/models.py:54,188,533,785,1033` — баннеры, бренды, иконки и изображения категорий, галерея товара), публичной загрузки на сайте нет; все девять опубликованных CMS-записей прода (3 `pages`, 3 `blog`, 3 `news`) встраиваний не содержат. То есть `DENY` ничего не сломал бы **сегодня**. Запас берётся под будущее: CMS-контент рендерится через `dangerouslySetInnerHTML` (`(blue)/[slug]/page.tsx:106`, `blog/[slug]/page.tsx:130`, `news/[slug]/page.tsx:121`, `privacy-policy/page.tsx:122`), значит редактор технически может вписать iframe в текст страницы, и упереться в жёсткий `DENY` неудобно.

Три вещи, без которых запас будет декоративным:

1. **Решает заголовок встраиваемого документа, а не встраивающего.** `<iframe src="/delivery">` внутри CMS-страницы блокируется заголовком от **Next**. nginx-статика отвечает за другой сценарий — встраивание файла из `/media/` в текст страницы. Поэтому `SAMEORIGIN` нужен в обоих местах, и правка только в nginx запаса бы не дала.
2. **`frame-ancestors` перекрывает `X-Frame-Options`.** Пара «`SAMEORIGIN` + `frame-ancestors 'none'`» в поддерживающих браузерах даёт запрет — CSP выигрывает. Значения обязаны идти согласованно, отсюда `'self'` в AC4.
3. **Админка остаётся строгой.** `/api/`, `/admin/`, `/swagger/`, `/redoc/` получают `DENY` + `frame-ancestors 'none'`: встраивать их незачем, а `'self'` открыл бы клик-джекинг на форму входа в админ-панель. `X_FRAME_OPTIONS = "DENY"` в Django уже стоит — трогать не надо, надо только не противоречить ему в CSP.

Побочное следствие для реализации: CSP существует в двух вариантах, различающихся ровно одной директивой, и после отказа от вложенных `include` живёт в четырёх файлах (три сниппета nginx + `next.config.ts`). Общего источника у Next и nginx нет и быть не может, поэтому расхождение ловится стражами (Task 2.4, 10.1, 10.4), а не архитектурой.

### Рекомендуемые значения

- `Strict-Transport-Security: max-age=31536000` — точка. Ни `includeSubDomains`, ни `preload` (обоснование выше).
- `X-Frame-Options: SAMEORIGIN` на HTML и на ресурсах nginx; `DENY` — только на локациях Django (это текущее значение `X_FRAME_OPTIONS`, менять его не надо). Сегодня на HTML приходят два конфликтующих значения, и защита от клик-джекинга находится в неопределённом состоянии — устранение этого и есть содержательная часть FR-41-06, а не «гигиена».
- `Referrer-Policy: strict-origin-when-cross-origin` — значение Next, строже текущего nginx-овского `no-referrer-when-downgrade`.
- `Content-Security-Policy: default-src 'self' http: https: data: blob: 'unsafe-inline'; frame-ancestors 'self'` на HTML и ресурсах nginx; та же строка с `frame-ancestors 'none'` — на локациях Django. Исходная политика переносится **посимвольно**, добавляется ровно одна директива.
- `Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=(), usb=(), magnetometer=(), gyroscope=(), accelerometer=()` — без `interest-cohort` (снята в Chrome 115+, даёт `Unrecognized feature` в консоли). `payment=()` безопасен: Payment Request API на сайте не используется, YuKassa работает редиректом.

### Порядок применения правок

- **nginx-конфиг без новых mount'ов** — `docker compose exec nginx nginx -t`, затем `docker compose exec nginx nginx -s reload`. Рестарт контейнера не нужен.
- **Первый раз, когда появился `snippets/`** — reload не поможет, bind-mount добавляется только пересозданием: `docker compose --env-file .env -f docker/docker-compose.yml up -d nginx`.
- **`next.config.ts` и `layout.tsx`** — `next.config.ts` в объёме, значит полная пересборка: `docker compose --env-file .env -f docker/docker-compose.yml up -d --build frontend`. `restart frontend` изменения конфига не подхватит. **После этого обязателен `docker compose restart nginx`** — см. врезку ниже.
- **Django settings** — `docker compose restart backend celery celery-beat`, после чего **обязательно** `docker compose restart nginx`: иначе nginx держит старый IP апстрима и отдаёт 502.
- **Прод** — вручную по SSH (шаг «Deploy to Production» в CI всегда пропускается). На проде `git fetch origin main; git reset --hard origin/main`, никакого `git pull`; `docker compose down -v` запрещён — снесёт volume с `media/` и `static/`.

> 🔴 **`restart nginx` после `up -d --build frontend` — не гигиена, а условие того, что падение будет видно.**
> `up -d --build frontend` **пересоздаёт** контейнер, фронт получает новый IP, а nginx держит старый и начинает отдавать 502. Дальше срабатывает `default.conf:232-233`:
> ```
> proxy_intercept_errors on;
> error_page 502 503 504 =200 /coming-soon/index.html;
> ```
> nginx перехватывает 502 и отдаёт заглушку «Скоро открытие» **со статусом 200**. Сайт молча превращается в заглушку, healthcheck по коду ответа молчит, и узнать об этом можно только открыв сайт глазами. Ту же ловушку та же стори ставит второй раз — сниппеты требуют `up -d nginx`, то есть пересоздания nginx.
>
> **Порядок на проде обязателен: сначала `up -d --build frontend`, затем `up -d nginx`.** В обратном порядке nginx поднимется, запомнит текущий IP фронта, и фронт уедет из-под него. После обеих команд — открыть `https://optisport.ru` глазами, до снятия таблицы AC13.

**Выкат этой стори (решение владельца 2026-08-25):** мерж в `develop`, затем прод **отдельным заходом в удобное окно** — срочности нет (см. шапку). 41.3 стартует параллельно, зависимости между стори нет: порядок в `sprint-status.yaml` отражает приоритет, а не блокировку. В `done` стори переводится после прод-замера (AC3, AC13), не по мержу. Пошаговый порядок команд — в плане выката (Task 13), а не только здесь: он должен быть открываем отдельно от стори, которую после закрытия никто не откроет.
