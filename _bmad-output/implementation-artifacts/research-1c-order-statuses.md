# Исследование: какие статусы заказа 1С может отдать сайту

Дата: 2026-11-23. Источники: исходники УТ 11.5.22.134 (`C:\Users\1\DEV\1C-PROJECT\src\cf`) и расширения
БУС 8.1.0.40 (`ext-src\bitrix-src`). Функция `СформироватьЗаказ` в 8.1.0.45 (прод) **побайтово совпадает**
с 8.1.0.40: сверено по `cfe-8145-raw`. Ещё использованы код `develop` (`6ab2928`) и логи nginx прода
за 30 дней (только чтение).

## 1. Главный вывод

1. **Сейчас статусы из 1С на сайт не приходят.** За 30 дней на проде 18 загрузок `type=sale&mode=file`,
   и все они — `contragents_*.xml`. Файлов заказов от 1С нет ни одного. В настройке обмена «в реальном
   времени» флаг «Выгружать заказы» выключен (см. память `1c-realtime-mode-no-orders`).
2. **Если включить выгрузку заказов в БУС как есть, сайт её не примет.** Импорт статусов
   (`OrderStatusImportService`) писали под другой формат. Расхождения перечислены в разделе 4.
3. **Статус БУС отдаёт одним значением.** Это строка «Ид статуса» из таблицы соответствий, которую
   администратор заполняет в 1С. Само значение 1С выбирает из одного из трёх источников (раздел 2).
   Оплата и отгрузка в этом же поле **вытесняют** этапный статус.

## 2. Что БУС пишет в `<Документ>` заказа

`БУС_ВыгрузкаСервер.СформироватьЗаказ`, CommerceML 3.1, `<ХозОперация>Заказ товара</ХозОперация>`:

| Поле | Значение |
|---|---|
| `<Ид>` | идентификатор, полученный от сайта (`order-{pk}`), иначе GUID заказа 1С |
| `<Номер>` | `НомерПоДаннымКлиента` — номер заказа на сайте |
| `<Номер1С>`, `<Дата1С>` | номер и дата документа в 1С |
| реквизит `Отменен` | `true`, если все строки отменены или заказ помечен на удаление |
| реквизит `Проведен` | проведён ли документ |
| реквизит **`Статуса заказа ИД`** | Ид статуса сайта, выбранный по правилу ниже. Пустой — реквизита нет |
| `Метод доставки ИД`, `Адрес доставки` | доставка |

`ДатаОплаты`/`ДатаОтгрузки` в документе заказа **нет**: строки «Дата оплаты по 1С» и «Дата отгрузки по 1С»
закомментированы. Даты приходят только отдельными документами оплат и отгрузок (раздел 3).

**Как выбирается `Статуса заказа ИД`** (первое сработавшее правило):

1. оплачено ≥ 100 % и отгружено ≥ 100 % → поле «Когда оплачен и отгружен»;
2. оплачено ≥ 100 % → поле «Когда оплачен» («Переводить в статус когда оплачен заказ»);
3. отгружено ≥ 100 % → поле «Когда отгружен» («Переводить в статус когда отгружен заказ»);
4. иначе — строка таблицы соответствий выбранного «Источника статусов заказов».

Проценты берутся из регистра `СостоянияЗаказовКлиентов` (`ПроцентОплаты`, `ПроцентОтгрузки`).
Настройки лежат в форме БУС «Сопоставление статусов заказов и отгрузок». Кнопка «Загрузить с сайта»
заполняет колонку «Ид статуса» списком сайта (`mode=info`, `ICExchangeView.handle_info`).

**Три источника статуса** (`ИсточникСтатусовЗаказов`):

### A. Статусы заказа (`СтатусыЗаказов`, по умолчанию) — их вручную ставит менеджер

| Перечисление `СтатусыЗаказовКлиентов` | Подпись в УТ |
|---|---|
| `НеСогласован` | На согласовании |
| `КОбеспечению` | К выполнению / В резерве |
| `КОтгрузке` | К отгрузке |
| `Закрыт` | Закрыт |

### Б. Состояния заказа (`СостоянияЗаказов`) — УТ вычисляет сама

Состояние хранится в регистре `СостоянияЗаказовКлиентов` и пересчитывается при движениях по заказу.
Формула — `Документ.ЗаказКлиента.ТекстЗапросаДляРасчетаСостоянийЗаказов`.

| Перечисление `СостоянияЗаказовКлиентов` | Подпись | Когда (упрощённо) |
|---|---|---|
| `ОжидаетсяСогласование` | Ожидается согласование | статус «На согласовании» |
| `ОжидаетсяАвансДоОбеспечения` | Ожидается оплата до обеспечения | нужен аванс, его нет |
| `ГотовКОбеспечению` | Готов к обеспечению | можно резервировать или заказывать товар |
| `ОжидаетсяПредоплатаДоОтгрузки` | Ожидается оплата до отгрузки | нужна предоплата перед отгрузкой |
| `ОжидаетсяОбеспечение` | Ожидается обеспечение | товара на складе хватает не на всё |
| `ГотовКОтгрузке` | Готов к отгрузке | всё обеспечено, отгрузки ещё не было, либо нужен расходный ордер |
| `ВПроцессеОтгрузки` | В процессе отгрузки | отгрузка начата, но не завершена (часть отгружена или есть «к отгрузке») |
| `ОжидаетсяОплатаПослеОтгрузки` | Ожидается оплата | отгружено, долг остался |
| `ГотовКЗакрытию` | Готов к закрытию | всё выполнено, заказ не закрыт |
| `Закрыт` | Закрыт | закрыт |

### В. Дополнительный реквизит заказа (`СвойствоЗаказов`)

Значения произвольные: их задаёт администратор, например «Передан на склад» или «Собирается».
Ставит их менеджер или склад вручную в карточке заказа.

## 3. Оплаты и отгрузки отдельными документами

Флаги «Выгружать оплаты» и «Выгружать отгрузки» в настройке БУС добавляют в тот же `<Контейнер>`
отдельные `<Документ>`:

- **оплата** — `ХозОперация` по типу документа, реквизиты `Оплачен`, `Номер оплаты по 1С`,
  `Дата оплаты по 1С`, `Метод оплаты ИД`. `<Номер>` = идентификатор оплаты, а не номер заказа;
- **отгрузка** — `ХозОперация` «Отпуск товара», `<Основание>` = Ид заказа, свой статус отгрузки
  (отдельная таблица соответствий), склад.

Флаги выключены — документы-«заглушки» выгружаются только для оплат и отгрузок, которые раньше
пришли с сайта. Сайт их не присылает, поэтому таких документов не будет.

## 4. Почему сайт сейчас не примет выгрузку БУС

| # | Что шлёт БУС | Что ждёт сайт | Последствие |
|---|---|---|---|
| 1 | архив `v8_*.zip` через `mode=file`, затем `mode=import&filename=orders_1_<uuid>.xml` | отдельный маршрут только для имени **ровно** `orders.xml` (`handle_file_upload` → `_handle_orders_xml`) | файл уходит в оркестратор импорта каталога (`ImportOrchestratorService`, `detect_file_type` → `all`), статусы не применяются. Что именно запустится — проверить тестом |
| 2 | реквизит `Статуса заказа ИД` | `СтатусЗаказа` из белого списка `ALLOWED_REQUISITES` (`orders/constants.py:124`) | документ отбрасывается как «no СтатусЗаказа requisite» |
| 3 | реквизит `Отменен` = `true` | не читается | отмена в 1С до сайта не доходит |
| 4 | документы оплат и отгрузок в том же контейнере | парсер берёт каждый `.//Документ` как заказ | при включённых флагах — ложные «заказ не найден» или конфликт номеров; нужен фильтр по `ХозОперация` |
| 5 | Ид статуса из списка `mode=info` | `STATUS_MAPPING` (`orders/constants.py:29`) | совместимо: список `mode=info` и есть ключи `STATUS_MAPPING`. Этапа «на складе» в списке нет |

Сопоставление с заказом совместимо: `<Номер>` = номер сайта, `<Ид>` = `order-{pk}`. Значит, 1С
обновляет **субзаказы**, а статус мастера пересчитывает существующая агрегация (`_aggregate_master_status`).

## 5. Этапы, о которых спрашивал владелец

| Этап | Что есть на сайте | Чем 1С может его отдать |
|---|---|---|
| 1. Заказ принят в обработку | `processing` ставится в момент выгрузки в 1С (спека `spec-order-processing-after-1c-export`, done) | статус «К выполнению / В резерве» (источник A) или состояние «Готов к обеспечению» / «Ожидается обеспечение» (Б). По сути дублирует то, что сайт уже показывает |
| 2. Заказ поступил на склад | **статуса нет**: между `processing`(3) и `shipped`(4) пусто | (A) «К отгрузке» — ставит менеджер; (Б) «Готов к отгрузке» — товар обеспечен и ждёт отгрузки, «В процессе отгрузки» — отгрузка начата; (В) доп. реквизит «Передан на склад» — ставят вручную |
| 3. Отгружен | `shipped` (есть), `shipped_at` (есть, из 1С не приходит) | «Когда отгружен» (100 % отгрузки) или состояния «Ожидается оплата» / «Готов к закрытию» |
| 4. Оплачен | отдельное поле `payment_status` + `paid_at`; из 1С не приходит | «Когда оплачен» (100 % оплаты) — но в том же поле статуса, что и этап; дата — только документом оплаты |

**Конфликт оплаты и этапа.** Правила 1–3 из раздела 2 стоят выше таблицы соответствий. Пусть клиент
оплатил до отгрузки, а настройка «Когда оплачен» заполнена. Тогда 1С с момента оплаты шлёт «оплачен»,
и этап «на складе» сайт уже не увидит. Чтобы этап и оплата шли раздельно, есть два пути:
(а) не заполнять «Когда оплачен» и брать оплату из документов оплат («Выгружать оплаты»);
(б) завести на сайте значения вида «Оплачен» в `STATUS_MAPPING` и класть их в `payment_status`,
не меняя `status`.

## 6. Что нужно для работающей цепочки

**Сайт:**
1. Маршрут для `orders_*.xml` из `type=sale` в `OrderStatusImportService`, а не в импорт каталога.
2. Реквизит `Статуса заказа ИД` в белом списке и в парсере.
3. Обработка `Отменен`.
4. Фильтр документов по `ХозОперация = «Заказ товара»`.
5. Новый статус этапа «на складе» с приоритетом между `processing` и `shipped`: константы, `mode=info`,
   фронтенд, админка. Решение за владельцем.
6. Тесты на реальном XML из БУС. Синтетику не изготавливать: снять выгрузку с `test_base`
   (настройка «Обмен локальный»).

**1С (администратор):** в настройке, которая забирает заказы по расписанию, включить выгрузку заказов
«только изменения». Выбрать источник статусов, нажать «Загрузить с сайта», заполнить соответствия
и поля «Когда оплачен» / «Когда отгружен».

**Проверить отдельно:** какие заказы БУС регистрирует к выгрузке — только пришедшие с сайта или все
`ЗаказКлиента`. Заказ без пары на сайте парсер пропустит, это безвредно, но засоряет лог.
И проверить, как на проде заполняются состояния: включены ли ордерный склад и резервирование.
От этого зависит, бывает ли вообще «Готов к отгрузке».
