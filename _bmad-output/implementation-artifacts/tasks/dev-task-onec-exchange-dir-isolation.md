# Задача: сегмент 1С, дождавшийся очереди, не находит своего файла (изоляция каталога обмена)

> Источник: `tech-debt.md` п. 26 («Каталог обмена 1С общий для всех сессий — изоляция отложена»).
> Предыдущая работа: стори `onec-import-cleanup-race-and-followups.md` закрыла удаление по glob-маске и тихий `COMPLETED` с нулём записей. Структурная причина осталась — эта задача про неё.
> Все координаты проверены чтением файлов на коммите `0fc2e4dc` (28.08.2026).
>
> **Канонический контракт на эту работу — `_bmad-output/specs/spec-onec-exchange-dir-isolation/` (SPEC.md + компаньоны).** Этот документ остаётся первоисточником нарратива; все решения, принятые после его написания, отражены в обоих местах и помечены здесь ✅/❌.

## 1. Симптом

Сессия обмена падает с сообщением:

```
Файлы, присланные 1С этому прогону, не прочитаны
(rests_1_1_74a08eed-….xml — не найден в каталоге обмена):
данные не попали в БД, а 1С их не повторит.
```

Файл физически приезжал и был принят (`Перенесено файлов: 1/1`), но к моменту, когда задача получила доступ к каталогу, его там уже не было.

## 2. Замеры прода (7 дней, 28.08.2026)

| Показатель | Значение |

| Сессий обмена за сутки | 1 509 (500 `mode=complete`, 1 009 `mode=import`) |
| Упавших сессий за 7 дней | 110 |

Корреляция полная: падает ровно то, что постояло в очереди. Разбивка по типам файлов:

| Тип сегмента | Падений |
|---|---|
| `rests` | 34 |
| `offers` | 18 |
| `goods` | 16 |
| `prices` | 15 |
| `groups` | 1 |
| `propertiesGoods` | 1 |

**Цена вопроса.** Сегодня это в первую очередь **недостоверный статус**: в разобранных случаях файл успевал прочитать сосед, то есть данные в БД попадали, но сессия отчитывалась провалом. Опасность в другом — настоящая потеря (инцидент 25.08.2026: 6 сегментов остатков, ≈18 000 строк, 963 варианта торговались по старым данным) выглядит **точно так же**. Пока падения идут пачками, отличить «файл прочитал сосед» от «файл не прочитал никто» можно только ручным разбором логов.

## 3. Механизм — по шагам

Разобрано на паре сессий 66453 / 66454 (28.08.2026, 04:50 UTC), воспроизводится и на 66628 (06:15 UTC).

| Время | Что произошло |
|---|---|
| 04:50:18.905 | Сессия **66453** создана по `mode=complete`, помечена `IN_PROGRESS`, задача ушла в Celery и **взяла лок каталога** |
| 04:50:20.954 | Сессия **66454** создана по `mode=import` с файлом `rests_1_1_74a08eed….xml` |
| 04:50:20.958 | Файл принят и положен в **общий** каталог `1c_import/rests/` |
| 04:50:20.961 | Задача 66454 ушла в Celery, но лок занят → `Каталог обмена занят другим импортом, задача отложена` |
| 04:50:21 | Держатель лока 66453 идёт по шагам импорта, доходит до `Обновление остатков из rests.xml`, собирает по маске **все** `rests/rests*.xml` — включая только что приехавший чужой файл — читает его и удаляет как «свой обработанный» |
| 04:50:30 | 66454 получает лок, ищет обещанный ей файл — его нет → `CommandError` → **FAILED** |

Три условия, каждое по отдельности корректное:

1. **Каталог общий.** `FileRoutingService.import_dir = import_base` — без сегмента сессии (`routing_service.py:79-81`).
2. **Чтение идёт по маске каталога, а не по обещанным именам.** `_collect_xml_files` собирает `prefix_*.xml` из подпапки типа (`import_products_from_1c.py`, метод `_collect_xml_files`), поэтому прогон забирает и чужие сегменты.
3. **Удаляется то, что прочитано.** `_cleanup_files` удаляет только реально распарсенные файлы и сверяет отпечаток (`import_products_from_1c.py:820-875`) — то есть удаление **законно**: файл действительно был прочитан этим прогоном. Гонка не в удалении, а в том, что файл вообще попал в чужой прогон.

## 4. Почему существующие guard'ы не закрывают

Их три, и все — «проверка в один момент времени», после которой конкурент появляется:

| Guard | Где | Почему не спасает |
|---|---|---|
| Пропуск cleanup при активных сессиях | `views.py:427-453` (`handle_init`) | Проверяет `IN_PROGRESS` **до** старта; сессия-жертва создаётся через 2 секунды после |
| Пропуск post-import cleanup | `tasks.py:486-506` | То же окно; к тому же файл убирает не он, а `_cleanup_files` |
| `defer_to_active_sessions` — прогон без обещания уступает дорогу | `tasks.py:414-423` | Считывается один раз на старте задачи. 66453 стартовала в 04:50:18, конкурент появился в 04:50:20 — на момент проверки его **не существовало** |

Классический TOCTOU на уровне сессий: между «посмотрел, кто активен» и «сгрёб каталог» проходят секунды, а 1С шлёт файлы каждые ~2 секунды.

## 5. Ключевой факт для выбора решения

**`session_key` уникален для каждого файла.** Замер: 85 сессий обмена за 20 минут → **85 разных ключей**. 1С не держит cookie-сессию между запросами, каждый файл приходит как новый обмен.

Из этого следует:

- изоляция вида `<import_dir>/<sessid>/<type>/` даёт **каждому файлу собственный каталог** — пересечься физически невозможно, гонка исчезает структурно, а не по договорённости;
- **`mode=complete` при этом остаётся без работы**: у него нет своих файлов, а чужие он больше не увидит. Сегодня 500 таких сессий в сутки сгребают каталог целиком — именно они чаще всего и оказываются держателем лока. Это не потеря функции: каждый файл уже импортируется собственной задачей;
- побочно закрывается мусор в `1c_temp` (32 276 пустых каталогов — по одному на каждую сессию, никогда не удаляются).

## 6. Развилка — ✅ РЕШЕНА (Alex, 28.08.2026): вариант 1

**Изображения приезжают отдельными запросами от XML.** Архив с картинками и `goods.xml` — это разные `sessid`. Сегодня они склеиваются в общем каталоге: XML ссылается на `import_files/<xx>/<file>.jpg`, и файл там лежит, потому что каталог один на всех.

При полной изоляции эта склейка ломается. Варианты:

- ✅ **Вариант 1 — ПРИНЯТ. Изолировать только XML-сегменты, `import_files` оставить общим.** Гонка наблюдается исключительно на XML (все 85 падений); картинки складываются аддитивно, перезапись одноимённого файла безопасна. Минимальная правка, целевой эффект достигается.
- **Вариант 2: изолировать всё, включая `import_files`.** Потребует связывать архив картинок с XML-сессией — механизма для этого нет, 1С такой связи не передаёт. Дорого и хрупко.
- ❌ **Вариант 2: изолировать всё, включая `import_files`** — отклонён.
- ❌ **Вариант 3: не изолировать, а резервировать** через `<import_dir>/.claimed/<session_pk>/` — отклонён: эквивалентен варианту 1 по эффекту, но добавляет третью раскладку поверх существующих `temp` / `import`.

> **Второе исключение из изоляции — флаг `.dry_run`.** Найдено при сверке кода, решено исполнителем как рутинный вызов: флаг остаётся в корне общего `import_base`. Он ставится оператором вручную по известному пути и является переключателем режима, а не данными обмена; уехав в сессионный каталог, он стал бы невидим для всех прогонов. Точки: `import_orchestrator.py:310` и `:421-424` (проверки), `routing_service.py:212` и `file_service.py:261-262` (защита от удаления) — все четыре должны смотреть на `import_base / ".dry_run"`.
> Маркер `.exchange_complete` изоляции не касается: он живёт в `session_dir` временного каталога (`file_service.py:283-296`), который и так был сессионным.

## 7. Задачи

### T1. Раскладка каталога обмена — по сессии *(ядро)*

- `FileRoutingService.__init__` (`routing_service.py:79-81`): `self.import_dir = self.import_base / session_id`. Снять комментарий `FIXED: Import directory should be shared/root` — он фиксирует ровно то поведение, которое чинится.
- Исключение для картинок: если `route_file` вернул `import_files/…`, файл кладётся в **общий** `import_base / "import_files"` (вариант 1 из развилки).
- `ImportOrchestrator` (`import_orchestrator.py`) передаёт задаче `data_dir` = каталог своей сессии. Команда импорта уже принимает `data_dir` параметром (`import_products_from_1c.py:339-341`) — **её править не нужно**, `_collect_xml_files` заработает как есть.
- ⚠️ **Уточнение по сверке кода (28.08.2026): у `ImportOrchestrator` собственная копия пути, мимо `FileRoutingService`** — `self.import_dir = Path(settings.ONEC_EXCHANGE["IMPORT_DIR"])` на `import_orchestrator.py:47`. Через неё идут распаковка zip (`:202`, `:214-217`), маршрутизация распакованного (`:260`, `:287`) и **оба** dispatch (`:344-346` и `:488-490`). Правки одного `routing_service.py` недостаточно — изоляция останется дырявой.
- Проверить путь копирования картинок: `variant_import.py` нормализует путь из XML (`import_files/xx/file.jpg`) и ищет его от `base_dir`. При общем `import_files` вне сессионного каталога `base_dir` для XML и для картинок станут разными — это единственное место, где нужна явная развязка.

### T2. `mode=complete` больше не сгребает каталог

- В `tasks.py` прогон без обещанных имён (`promised_filenames is None`) при сессионной раскладке видит только свой пустой каталог. Убедиться, что он завершается `COMPLETED` с честной записью «своих файлов нет», а не пытается импортировать пустоту.
- ✅ **Решено (Alex, 28.08.2026): запись идёт пометкой в поле `report` сессии** (`tasks.py:480-482`, туда уже накапливаются строки вида `[{timestamp}] …`). Отдельного поля и миграции не требуется; тест из T4 вешается на подстроку в `report`.
- `defer_to_active_sessions` (`tasks.py:414-423`) после изоляции становится избыточным для этого сценария — **не удалять**, оставить как страховку для ручных прогонов с `data_dir` по умолчанию.

### T3. Уборка своего каталога

- `cleanup_import_dir` теперь чистит **свою** папку — это снимает `risk: CRITICAL` с метода (13 impacted, 7 процессов), потому что удаление физически не может задеть соседа. ⚠️ **Перед правкой обязателен `npx gitnexus impact cleanup_import_dir --direction upstream`** — метод правили уже двумя хотфиксами (`ff0bbc0a`, `057afc41`).
- Добавить удаление каталога сессии в `1c_temp` после завершения обмена (сейчас копится 32 276 пустых папок).
- Предусмотреть уборку осиротевших сессионных каталогов: при падении воркера папка останется навсегда. ✅ **Порог решён (Alex, 28.08.2026): 24 часа** — упавший каталог доживает до утра и пригоден для ручного разбора. Механизм — периодическая `celery-beat` задача.
- ❌ **Разовая зачистка уже накопленных 32 276 каталогов в область работы НЕ входит** — Alex делает её вручную (решение от 28.08.2026). Миграцию или management-команду под это писать не нужно. Следствие для приёмки: база сравнения по п. 5 контракта — снимок счётчика **после** ручной зачистки, а не 32 276.

### T4. Тесты

- **Регрессионный, обязателен:** две сессии с разными `session_key`, файлы одного типа (`rests_1_1` и `rests_1_2`), задачи запускаются последовательно с занятым локом — обе обязаны прочитать **свой** файл и завершиться `COMPLETED`. Этот тест на текущем коде должен **упасть** (показать RED), иначе он ничего не ловит.
- Прогон `mode=complete` при наличии чужих сессионных каталогов не читает и не удаляет ничего из них.
- Картинки: XML из сессионного каталога находит файл в общем `import_files`.
- Уборка: `cleanup_import_dir` сессии A не трогает каталог сессии B.

## 8. Контракт приёмки

1. Две сессии обмена, приехавшие в пределах времени обработки одна другой, обе завершаются `COMPLETED` и каждая читает ровно свой файл.
2. Падений с текстом «не найден в каталоге обмена» на проде за сутки — **0** (сегодня 85 за 7 дней, все после ожидания лока).
3. Ни один сегмент не остаётся непрочитанным: сумма обработанных сегментов за выгрузку равна числу присланных файлов.
4. `mode=complete` не удаляет файлов, принадлежащих другим сессиям, — проверяется тестом, а не наблюдением.
5. `1c_temp` и `1c_import` не накапливают каталоги: после завершения обмена число папок возвращается к исходному и не растёт от обмена к обмену. База сравнения — снимок счётчика после ручной зачистки исторического мусора (см. T3), а не 32 276.
6. Регресс импорта 1С зелёный целиком (`apps/products apps/integrations`, на 28.08 — 605 тестов).

## 9. Ограничения проекта — читать до первой команды

- **Только Docker + PostgreSQL.** Тесты: `cd docker && docker compose -p freesport-test -f docker-compose.test.yml run --rm -T backend pytest …`. `--env-file` тестовому compose не передаётся; `run --rm`, не `exec`. Параллельные прогоны по одному compose-проекту невозможны — одна БД на проект.
- **Синтетические XML запрещены**, используются реальные выгрузки из `data/import_1c/`.
- **GitNexus обязателен:** `impact --direction upstream` до правки каждого символа, `detect-changes --scope all` перед коммитом. Только CLI, MCP отключён.
- **Комментарии и docstrings — на русском** (стиль проекта).
- **Деплой ручной**, CI-шаг всегда skipped; после пересборки backend обязателен `restart nginx`, а `celery` и `celery-beat` пересобираются вместе с backend — импорт живёт в воркере.

## 10. Как проверить на проде после выката

```sql
       count(*) FILTER (WHERE status = 'failed') AS failed
FROM import_sessions WHERE created_at > now() - interval '24 hours';

-- 2. Ожидание лока может остаться, падения после него — нет
SELECT count(*) FROM import_sessions
WHERE status = 'failed' AND report LIKE '%Каталог обмена занят%'
  AND created_at > now() - interval '24 hours';
```
