# Задача: обновлённые фото из 1С не становятся главными (синхронизация состава изображений)

Собрано 2026-08-27. Ветка `main`, коммит `1c0fac85`. Все цифры — замеры на проде
`optisport.ru` (БД + `media` внутри контейнера backend), не рассуждение.

---

## 1. Симптом

Заявка: «в 1С обновили фото, они не попали в БД». Товар
`gantel-vinilovaja-espado-es1119lpk-svetlo-rozovyj-1-para` (id 9194,
`onec_id = 6bf4cc2c-1319-11f1-973b-f9cdeb93e398`).

Фото **попало** в БД. Состав `base_images`:

| Позиция | Файл | Размер | Появился в `media` | Что на картинке |
|---|---|---|---|---|
| 1 | `6bf4cc2c-…_50c67024-13eb-11f1-….png` | 14 КБ | 27.04.2026 | белая гантель 0,5 кг — **чужой товар** |
| 2 | `6bf4cc2c-…_fb2f7292-94c7-11f1-….jpg` | 147 КБ | **25.08.2026** | розовая гантель 1,0 кг — верное фото |

API отдаёт главным первый элемент списка:

```
"main_image": "/media/products/base/6b/6bf4cc2c-…_50c67024-….png"
```

Новое фото доступно только вторым в галерее. У всех пяти вариантов товара
`main_image` пуст, `gallery_images` пусты — `offers.xml` картинок не содержит,
весь состав живёт в `Product.base_images`.

**Формулировка дефекта:** импорт умеет добавлять картинки и не умеет
поддерживать состав. Снятое в 1С фото не удаляется, порядок 1С не применяется,
главное изображение не переназначается.

## 3. Как работает сейчас

Всё в `backend/apps/products/services/variant_import.py`.

**Путь на проде — только XML.** Список картинок берёт парсер из тегов `<Картинка>`
(`services/parser.py:313` для goods, `:364` для offers) и кладёт в
`goods_data["images"]`. Оттуда — `_import_base_images` (вызовы на `:556` и `:614`)
и `_import_variant_images` (`:830`, `:917`).

Второй путь — сканирование каталога глобом по `onec_id`
(`management/commands/import_images_from_1c.py`, `integrations/tasks.py:192`) —
**на проде не исполняется**: сессий с `import_type='images'` в базе ноль.

**`_import_base_images:647` аддитивен.** Существующий список предзагружается в
`base_images`/`seen_filenames` (`:665-675`), новые пути дописываются в хвост
(`:694`). Удаления нет, переупорядочивания нет. Сравнение на `:703` фиксирует
только факт роста списка.

**`_import_variant_images:934` аддитивен и не переназначает главное.**
`main_image_set = bool(variant.main_image)` (`:949`), далее `if not main_image_set`
(`:987`) — уже заполненное главное изображение заменить нельзя конструктивно.

**`_save_image_if_not_exists:380`** копирует файл, если его ещё нет в хранилище
(`:426`), и **считает ошибкой отсутствие исходника** (`:403-406`) — даже когда
копия давно лежит в `media`. Это и есть источник 253 ошибок на прогон:
1С подчищает `import_files` после импорта (`import_products_from_1c.py:878-904`),
а `goods.xml` с теми же товарами приходит снова.

Ни сравнения размера, ни `mtime`, ни хэша: `grep hashlib|md5|st_mtime|checksum`
по файлу — 0 совпадений. Флагов `--force`/`--overwrite` нет ни в одной команде
импорта. `_clear_existing_data` (`import_products_from_1c.py:907`) чистит только
записи БД, `media` не трогает.

**Порог размера.** `MIN_IMAGE_SIZE_BYTES = 100 КБ` (`:358`), резервный
`FALLBACK_MIN_IMAGE_SIZE_BYTES = 8 КБ` (`:360`), выбор — `_get_effective_min_size:362`,
и он смотрит **только на исходники**. Мелкое превью, попавшее раньше по
резервному порогу, остаётся в составе навсегда и первым.

## 4. Задачи

Порядок не произвольный: **T1 — предусловие T2 и T3**. Без него зеркалирование
состава на сегодняшнем проде обрежет каталог, потому что исходников нет и
«разрешить» картинку не по чему.

### T1. Уже перенесённая копия — не потеря *(предусловие, критично)*

`_save_image_if_not_exists` при отсутствии исходника обязан проверить, лежит ли
копия по целевому пути в хранилище, и вернуть её как валидный результат
(со счётчиком `skipped`, не `errors`). Ошибкой считать только случай «нет ни
исходника, ни копии».

Эффект помимо разблокировки T2: 195 тыс. ложных ошибок в сутки исчезают, счётчик
`images_errors` снова начинает что-то значить.

### T2. `Product.base_images` — зеркало `goods.xml`

Состав и порядок берутся из выгрузки: снятая в 1С картинка уходит из списка,
первой становится первая картинка 1С. Обязательные защиты:

- если **ни одна** картинка из XML не разрешилась — состав не трогать (сбой
  выгрузки не равен «фото удалили»);
- если у товара в выгрузке нет тега `<Картинка>` вовсе (`"images" not in goods_data`)
  — состав не трогать; удаление всех фото через обмен не поддерживается осознанно;
- зеркалить **только** список из XML. Сканирование каталога источником истины не
  является — там список собран по остаткам на диске, и режим обязан остаться
  аддитивным.

### T3. `ProductVariant.main_image` переназначается по `offers.xml`

Первая картинка выгрузки становится главной, остальные — галереей в порядке 1С.
Защиты те же, что в T2. Сейчас на проде `offers.xml` картинок не содержит, то
есть задача профилактическая — но `if not main_image_set` (`:987`) делает
обновление невозможным конструктивно, и это надо снять вместе с T2, иначе
поведение товара и варианта разъедется.

### T4. Порог размера считать и по копиям в `media`

`_get_effective_min_size` смотрит только на исходники. После T1 исходников на
проде обычно нет — порог упадёт до резервных 8 КБ, и мелкие превью, ранее
отсеянные, вернутся в состав. Размер нужно брать и с перенесённой копии.

### T5. Обновление содержимого при совпадении имени файла *(латентный)*

`_save_image_if_not_exists:426` пропускает файл по факту существования имени, без
сравнения содержимого. На разобранном случае это **не сработало** — 1С при замене
фото создала новый объект картинки с новым GUID, имя файла изменилось
(`50c67024-…` → `fb2f7292-…`), копирование прошло. Но если 1С когда-нибудь
перезапишет содержимое под тем же GUID, обновление не доедет молча.

Решается сравнением размера (дёшево) или хэша (надёжно) исходника и копии.
Отдельная задача, не блокирует T1–T4, приоритет ниже.

### T6. Историческая чистка состава

T2 выправляет товар только когда 1С пришлёт его в `goods.xml`, а инкрементальный
обмен гоняет фиксированные 129 товаров — гантель id 9194 сама не придёт.
Развилка вынесена в §5.

### T7. Наблюдаемость импорта изображений

253 ошибки на каждый прогон, 195 тысяч в сутки, полтора месяца — и ни одного
сигнала. `report_details` их пишет (`variant_import.py:2311`), текстовый `report`
сессии про изображения не пишет ничего: `report ILIKE '%изображен%'` по всей
таблице — 0 строк. Нужен порог, при котором доля неразрешённых картинок попадает
в `report` сессии и в лог как предупреждение, а не растворяется в счётчике.

### T8. `Path(variant.main_image)` падает с `TypeError` *(мелкий)*

`variant_import.py:958`: `main_image` — `ImageField`, `Path()` от `ImageFieldFile`
кидает `TypeError: argument should be a str or an os.PathLike object`. Ветка
достижима в аддитивном режиме при непустом `main_image` — то есть в команде
`import_images_from_1c` на товаре, у которого главное фото уже стоит. Резать
путь нужно по `.name`.

### T9. Вопросы к стороне 1С *(вне бэкенда)*

Не задачи разработки, но без ответов T2 работает вхолостую:

1. Почему `goods.xml` ссылается на 253 картинки, файлы которых не передаются?
   Ожидаемо: либо файлы идут отдельным архивом и теряются, либо в настройках
   обмена выгрузка картинок выключена, а ссылки остаются.
2. Почему одна и та же порция из 129 товаров уходит каждые 5 минут, `created = 0`,
   `updated = 129`? Регистрация изменений не снимается — обмен работает вхолостую
   и создаёт ~1 900 сессий импорта в сутки.
3. Перечисляет ли `<Картинка>` **весь** актуальный состав фото товара, или только
   изменённые? От этого зависит, законен ли T2 в принципе (см. §5).

## 5. Развилки — решает Alex, не исполнитель

**Развилка А: законность зеркалирования (блокирует T2).**
T2 исходит из того, что `<Картинка>` в `goods.xml` перечисляет полный актуальный
состав фото товара — так устроен CommerceML. Если конкретная выгрузка БУС шлёт
только изменённые картинки, зеркало **удалит легитимные фото**. Проверяется
одним прогоном: зарегистрировать товар 9194 к обмену в 1С и перехватить
`goods.xml` до того, как импорт подчистит каталог. **Сделать до реализации T2.**

**Развилка Б: чем чинить исторические 104+ товара.**

*Б1 — полная выгрузка из 1С.* После T1–T4 зарегистрировать всю номенклатуру к
обмену. Состав выправится по данным 1С, точно и без эвристик; файлы картинок
пересылать не обязательно — копии уже в `media`, T1 их узнает.
Минус: зависит от развилки А и от готовности стороны 1С; при текущем зацикленном
обмене полная выгрузка утонет в очереди.

*Б2 — существующая команда `deduplicate_images`.* Инструмент уже написан:
`python manage.py deduplicate_images --min-size 100` удаляет из `base_images`
файлы мельче порога, а у вариантов заменяет мелкий `main_image` на первый
подходящий из галереи (`deduplicate_images.py:173-186`, `:285-292`). Защита от
обнуления есть — если после фильтрации не осталось ничего, первый файл
возвращается (`:179-184`). Покрывает ровно те 104 товара.
Минус: эвристика по размеру, а не данные 1С; «крупное заменили крупным» не ловит;
на проде, судя по 104 живым случаям, её ни разу не запускали — сначала `--dry-run`.

Рекомендация: **Б2 сразу после T1–T4** как быстрое лечение видимого симптома,
**Б1 следом** как приведение к данным 1С. Порядок важен: Б2 до T1 бессмысленен —
следующий импорт вернёт мелкую картинку в хвост, а не в голову, но состав снова
поедет.

## 6. Контракт приёмки

- [ ] Повторный `goods.xml` с теми же товарами **не даёт ошибок** `Image not found`
      для картинок, копии которых лежат в `media`. На проде `images_errors` в
      goods-сессии падает с 253 до величины, объяснимой реально отсутствующими
      файлами.
- [ ] Фото, снятое с товара в 1С, **уходит** из `base_images` при следующей
      выгрузке этого товара.
- [ ] Порядок картинок в `base_images` совпадает с порядком `<Картинка>` в
      `goods.xml`; главным становится первое.
- [ ] Выгрузка, в которой **ни одна** картинка не разрешилась, состав **не меняет**.
      Тест обязателен — это единственная защита от потери каталога при сбое обмена.
- [ ] Товар, у которого в выгрузке нет `<Картинка>`, состав не меняет.
- [ ] Мелкое превью не возвращается в состав после того, как исходники подчищены
      (порог считается и по копиям в `media`).
- [ ] Режим сканирования каталога (`import_images_from_1c`) остался аддитивным —
      тест фиксирует, что он состав не режет.
- [ ] `import_images_from_1c` на товаре с непустым `main_image` не падает
      (T8).
- [ ] Каждый тест **падает до правки**. Прогнать и показать RED, иначе тест
      ничего не ловит.
- [ ] Товар 9194 после выката и выгрузки отдаёт `main_image` = розовая гантель
      1,0 кг (`…_fb2f7292-….jpg`).

## 7. Ограничения проекта — читать до первой команды

- **Тесты только через Docker с PostgreSQL:**
  ```bash
  cd docker && docker compose -p freesport-test -f docker-compose.test.yml run --rm -T backend \
    pytest -xvs apps/products/tests/<файл>
  ```
  `--env-file` тестовому compose не передаётся; `run --rm`, не `exec`.
  **Параллельные прогоны по одному проекту невозможны** — одна БД на проект, две
  сессии дерутся на `TRUNCATE` и дают лавину ложных падений.
- **Синтетические XML для тестов импорта 1С запрещены** — только реальные файлы
  из `data/import_1c/` (каталог под широким правилом `.gitignore`, новые файлы —
  через `git add -f`). Для тестов самих методов состава достаточно временных
  файлов-заглушек нужного размера: XML там не участвует.
- **`MEDIA_ROOT` в тестах обязателен через `override_settings`** — методы пишут в
  `default_storage`, без изоляции тест насорит в рабочий `media`.
- **GitNexus обязателен.** До правки `_import_base_images`, `_import_variant_images`,
  `_save_image_if_not_exists`, `_get_effective_min_size` — `npx gitnexus impact <symbol>
  --direction upstream`, сообщить blast radius (на 27.08 по обоим методам импорта —
  LOW, 9 узлов, 4 прямых вызывающих). Перед коммитом — `npx gitnexus detect-changes
  --scope all`. MCP-инструменты `gitnexus_*` отключены, только CLI.
- **Деплой на прод ручной**, CI-шаг всегда skipped. После пересборки backend
  **обязателен `restart nginx`**, иначе весь внешний API и обмен 1С уходят в 502.
- **Миграций задача не требует** — меняется только логика заполнения существующих
  полей.

## 9. Контекст: разобранная и отклонённая гипотеза

Параллельно рассматривалась версия, что корневая причина — skip в
`_save_image_if_not_exists:426`: якобы GUID картинки в 1С стабилен, имя файла при
замене фото не меняется, `default_storage.exists()` возвращает True и новый
контент не копируется.

**Опровергнуто фактами:** у товара 9194 GUID картинки у нового фото другой
(`fb2f7292-94c7-11f1-…` против `50c67024-13eb-11f1-…`), файл скопирован 25.08,
`base_images` изменился и содержит оба пути. По каталогу за 25.08 — 152
скопированных файла при нуле ошибок. Если бы skip-по-имени блокировал обновление,
новых файлов в `media` не появлялось бы вовсе.

Из той версии в работу взято одно верное наблюдение — отсутствие сравнения
содержимого как **латентный** дефект: это T5, а не корневая причина.

Реализация T1–T4 + T8 была прототипирована и проверена 27.08 (11 новых тестов,
прогон импорта 1С — 330 passed, 1 skipped), после чего откачена по решению Alex:
задача была поставлена как проверка, не как правка. Бриф содержит достаточно,
чтобы повторить осознанно, а не восстанавливать патч вслепую.
