# Задача: чистка недостоверных записей `marketing_email` в журнале согласий

**Заведена:** 2026-08-24, на круглом столе по эпику 41.
**Статус:** не начата. **Вне объёма эпика 41** (решение Alex, 2026-08-24).
**Владелец:** не назначен.

## Проблема

Эндпоинт подписки на рассылку создаёт **две** записи `UserConsent` из **одного** фронтового чекбокса `pdp_consent`:

```python
# backend/apps/common/views.py:427-428
UserConsent.objects.create(consent_type="pdp_contract", **consent_kwargs)
UserConsent.objects.create(consent_type="marketing_email", **consent_kwargs)
```

Пользователь даёт согласие на обработку персональных данных, а в журнал дополнительно попадает согласие на **рекламную коммуникацию**, которого он не давал.

**Срок экспозиции:** двойная запись внесена коммитом `28c0a0a0` (стори 35.3) **13.05.2026**. На 24.08.2026 — три с половиной месяца в проде.

## Почему это отдельная задача, а не таск внутри стори 41.3

Стори 41.3 эпика 41 правит **код** — останавливает появление новых недостоверных записей. Эта задача правит **данные прода**: операция необратима, требует иной процедуры выката и отдельного подтверждения. Смешивать обратимую правку кода с необратимой операцией над данными нельзя (решение круглого стола, Winston).

**Порядок жёсткий:** сначала стори 41.3 (останавливает запись), затем эта задача (чистит накопленное). В обратном порядке эндпоинт допишет новые записи, пока идёт чистка.

## Что нужно сделать

1. **Снять число.** Сколько записей `UserConsent` с `consent_type="marketing_email"`, созданных через подписку начиная с 13.05.2026. Форма починки зависит от порядка величины: десятки — правка вручную, тысячи — миграция данных.
   - Использовать навык `production-database`.
   - Отделить записи, созданные **регистрацией**: там код корректен (`backend/apps/users/views/authentication.py:151` пишет `marketing_email` только при `_marketing_consent`), эти записи достоверны и трогать их **нельзя**.
   - Признак разделения: записи из подписки имеют парную `pdp_contract` с тем же `given_at`, `ip_address` и `user_agent`; у анонимных подписчиков заполнен `session_key`, а `user` пуст.

2. **Не удалять `pdp_contract`.** В том же вызове создаётся достоверная запись согласия на обработку ПДн — её пользователь действительно дал. Удалению подлежит только `marketing_email`.

3. **Выбрать форму:** физическое удаление или пометка недостоверной. Пометка требует нового поля в модели; удаление проще, но лишает следа.

4. **Зафиксировать факт чистки.** Что удалено, сколько, на каком основании, кем и когда. Тихое удаление недопустимо: журнал согласий — доказательственный документ, и операция над ним сама должна быть доказуема (требование Paige).

## Риск, если не делать

Журнал согласий используется как основание для рассылки. При запуске рассылки письма уйдут части подписчиков, не дававших согласия на рекламу, — при наличии в системе записи, утверждающей обратное. По ФЗ-152 ст. 9 и ФЗ-38 нарушением является именно **действие на основании недостоверной записи**, а не отсутствие чекбокса.
