## 1. Зачем

Первая редакция патча (выполнена на `test_base` 2026-08-01, на прод **не переносилась**) выгружает
блок `<ЗначенияРеквизитов>` только тем контрагентам, у которых есть действующее соглашение с
видом цен — 485 из 4735. Остальные приходят без блока.

Из-за этого на портале два принципиально разных события выглядят одинаково:

| Что произошло в реальности | Что видит портал |
|---|---|
| У клиента нет действующего соглашения | блока нет |
| Патч затёрт обновлением модуля БУС | блока нет |

Последствие, найденное при разборе стори эпика 40: поле `User.onec_price_type_id` нельзя ни
гасить, ни сохранять безопасно. Гасить — при поломке выгрузки данные обнулятся у всех
контрагентов разом. Сохранять — привязка заявки (`link_1c_customer`, FR-40-11) выдаст клиенту
роль по соглашению, снятому в 1С месяцы назад, без единой ошибки в логах.

**Решение:** отсутствие соглашения выгружать **явно**. Тогда «нет блока» означает ровно одно —
патч в расширении затёрт.

## 2. Что меняется в выгрузке

Контрагент **с** действующим соглашением — как сейчас, без изменений:

```xml
<ЗначенияРеквизитов>
  <ЗначениеРеквизита><Наименование>ТипЦенId</Наименование><Значение>a91bdb02-…</Значение></ЗначениеРеквизита>
  <ЗначениеРеквизита><Наименование>ТипЦенНаименование</Наименование><Значение>Опт 2 (150-300 тыс.руб в квартал)</Значение></ЗначениеРеквизита>
  <ЗначениеРеквизита><Наименование>СоглашениеНаименование</Наименование><Значение>Опт 2</Значение></ЗначениеРеквизита>
  <ЗначениеРеквизита><Наименование>СоглашениеТиповое</Наименование><Значение>true</Значение></ЗначениеРеквизита>
</ЗначенияРеквизитов>
```

Контрагент **без** соглашения — блок теперь тоже выгружается:

```xml
<ЗначенияРеквизитов>
  <ЗначениеРеквизита><Наименование>СоглашениеСтатус</Наименование><Значение>НетСоглашения</Значение></ЗначениеРеквизита>
</ЗначенияРеквизитов>
```

Итог: блок приходит у **каждого** контрагента пакета. Прирост объёма — одна пара
`Наименование`/`Значение` на ~4250 контрагентов, пренебрежимо.

### Чего делать нельзя

- **Не писать `НетСоглашения` в `ТипЦенId`.** Это поле под GUID: портал нормализует его к
  нижнему регистру и ищет в справочнике `PriceType`. Слово в поле GUID первый же разработчик
  сочтёт мусором из 1С и отфильтрует. Статус — отдельный реквизит.
- **Не выгружать пустой `ТипЦенId`** рядом со статусом. У контрагента без соглашения GUID
  отсутствует, а не пуст.

## 4. Правка `03_code.bsl`

Сейчас блок собирается и присваивается только внутри двух вложенных условий:

```bsl
Если НЕ ВыполненныйЗапросВЦ.Пустой() Тогда
    …
    Если ЗначенияРеквизитовКонтрагентаXDTO.ЗначениеРеквизита.Количество() > 0 Тогда
        КонтрагентXDTO.ЗначенияРеквизитов = ЗначенияРеквизитовКонтрагентаXDTO;
    КонецЕсли;
КонецЕсли;
```

Требуемое поведение:

1. XDTO-объект блока создаётся **всегда**, до проверки пустоты выборки.
2. Цикл по выборке видов цен выполняется как сейчас (включая `Продолжить` при незаполненном
   `ВидЦен` — защита остаётся).
3. Если после цикла **ни одного реквизита не добавлено** (выборка пуста либо все виды цен
   оказались незаполненными), добавляется единственный реквизит
   `СоглашениеСтатус` = `"НетСоглашения"` строкой.
4. `КонтрагентXDTO.ЗначенияРеквизитов` присваивается **безусловно** — блок пустым уже быть
   не может.

Существующая процедура `ДобавитьЗначениеРеквизитаXDTO(…)` принимает и строки, и булево
(`СоглашениеТиповое`), поэтому новых вспомогательных функций не нужно. Маркеры
`//FREESPORT: вид цен клиента — начало / конец` сохранить: по ним правка переносится при
обновлении модуля БУС.

## 5. Почему XSD не меняется

Вставленный первой редакцией элемент ссылается на **предсуществующий** тип
`type="tns:ЗначениеРеквизита"` — обобщённую пару `Наименование`/`Значение`. Схема не
перечисляет допустимые наименования реквизитов, поэтому новое наименование `СоглашениеСтатус`
проходит без правки макета `Справочник.БУС_НастройкиОбмена.СхемаXSDОбмена`.

Практическое следствие: если первая редакция уже наложена на тестовую базу, XSD трогать не надо —
перезаливается только `CommonModules\БУС_ВыгрузкаСервер.xml`.

## 6. Порядок работ

1. Откатить модуль на тесте до непропатченного состояния (`Module.bsl.orig` рядом с модулем либо
   `restore-ext-8140.ps1`). **Причина:** `patch_bus_module.py` идемпотентен по маркеру `FREESPORT` —
   на уже пропатченном модуле он напечатает «правка уже применена» и вторую редакцию не наложит.
2. Поправить `fragments/03_code.bsl`.
3. Наложить патч заново, перезалить `CommonModules\БУС_ВыгрузкаСервер.xml` пообъектно.
4. Выгрузить контрагентов с `test_base`, проверить обе ветки: есть контрагенты с непустым
   `ТипЦенId` и есть контрагенты со статусом `НетСоглашения`; контрагентов **без** блока нет.
5. Переснять `backend/data/import_1c/contragents_pricetype/` — на этом снимке строятся тесты
   эпика 40 (каталог `data/import_1c` в git игнорируется).
6. Снять новую тройку показателей для README: всего контрагентов / с непустым `ТипЦенId` /
   со статусом `НетСоглашения`.
7. Обновить README и §6 родительского задания.
8. Передать администратору 1С патч **второй редакции** для переноса на прод.

Операционные ограничения (версия платформы, пообъектная загрузка, PowerShell-лаунчеры, откат) —
в `README.md`, §«Как применить». Здесь не дублируются.

## 7. Открытые вопросы

| # | Вопрос | Рекомендация |
|---|---|---|
| 1 | Писать `СоглашениеСтатус` **только** при отсутствии соглашений или всегда (`Действует` / `НетСоглашения`)? | Только при отсутствии — как решено. Блок и так приходит у всех, детектор регресса считает блоки, а не статусы. «Всегда» добавляет строку каждому контрагенту без нового смысла |
| 2 | Контрагент с незаполненным `Партнер` (соглашения искать не по чему) | Получает `НетСоглашения`. Для портала это то же самое: вида цен нет, роль не выводится, поле гасится |
| 3 | Маркетплейсы (несколько соглашений на одном виде цен) | Ничего не меняется: у них есть соглашения, статус не пишется, дедупликация GUID остаётся на стороне портала |
