## Задача 1. `OSError` при разрешении пути выдаётся за «чужой тест»

### Что не так

`_relative_parts` (`backend/conftest.py:107`) заканчивается так:

```python
    try:
        return Path(str(path)).resolve().relative_to(BACKEND_ROOT).parts
    except (ValueError, OSError, RuntimeError):
        return OUTSIDE_BACKEND
```

Три исключения означают разное, а результат один:

| Исключение | Что произошло на самом деле |
|---|---|
| `ValueError` | путь разрешился, но ведёт за пределы `backend/` — **тест действительно чужой** |
| `OSError` | путь не разрешился: превышение MAX_PATH на Windows, петля симлинков, недопустимые символы, права на bind-mount |
| `RuntimeError` | то же — не разрешился |

Дальше по коду (`backend/conftest.py:181`) все три получают причину `REASON_OUTSIDE` = `"путь вне backend/"`,
а совет (`backend/conftest.py:216`) — «перенесите его под `backend/`». Для файла, который **уже лежит
внутри** `backend/`, этот совет невыполним, а диагноз указывает не туда.

### Почему это важно именно сейчас

До ужесточения ошибка стоила одной строки в сводке предупреждений. Теперь при заданном `-m`
и выпадении элемента она обрывает прогон — то есть разработчик на Windows (основная платформа Alex)
с длинным путём внутри `backend/` получает красный прогон и совет, ведущий в тупик.

### Решение

Развести случаи третьим сентинелом рядом с существующим `OUTSIDE_BACKEND` (`backend/conftest.py:68`):
`UNRESOLVABLE` + своя причина + свой совет.

**Открытый вопрос, который надо решить осознанно (и назвать решение в комментарии):** должен ли
`UNRESOLVABLE`-элемент поднимать гейт? Аргументы обеих сторон:

- **Да:** тест всё равно не размечен и всё равно выпадет из отбора — молчание вернёт ровно ту тишину,
  ради устранения которой хук написан.
- **Нет:** причина в среде, а не в расположении файла; выполнимого действия у разработчика нет,
  и обрыв прогона превращается в блокировку без выхода.

**Рекомендация:** предупреждать, но не рвать — и явно написать в тексте, что путь не удалось разрешить,
с указанием исходного пути и типа исключения. Действие в этом случае неочевидно, а красный прогон
без выполнимого совета хуже громкого предупреждения. Но это именно рекомендация, не данность.

### Границы

- Не трогать `ValueError`-ветку: она классифицирует верно.
- Не пытаться «чинить» сам длинный путь или симлинк — задача только про честный диагноз.
- Совет для `REASON_PATHLESS` (элемент сбора без файла) уже разведён — не ломать его.

## Задача 2. Сверка выпавших по `id()` ломается на плагинах, пересоздающих `items`

### Что не так

`backend/conftest.py:329-334`:

```python
    survived = {id(item) for item in items}
    dropped = [entry for entry in unmarkable if id(entry[0]) not in survived]
```

Сейчас **корректно**, и это проверено: `unmarkable` хранит сами элементы, поэтому пока ссылка жива,
её `id` не может достаться другому объекту. Комментарий в коде этот инвариант называет.

Дыра в другом: сверка предполагает, что `items` **фильтруется на месте** и уцелевшие остаются
теми же объектами. Плагин, который пересобирает список новыми объектами (размножители тестов
вроде `pytest-flakefinder`), сделает «выпавшими» **сразу все** неразмечаемые элементы — и при
непустом `-m` прогон оборвётся без причины.

В текущем окружении таких плагинов нет (проверено: `backend/requirements.txt`), поэтому это защита
на вырост, а не починка сломанного.

### Решение

Считать элемент уцелевшим, если среди `items` нашёлся его `id` **или** его `nodeid`:

```python
survived_ids = {id(item) for item in items}
survived_nodes = {getattr(item, "nodeid", None) for item in items}
```

`nodeid` переживает пересоздание объекта, поэтому ложных срабатываний не будет. У элемента без
`nodeid` (см. `PathlessItem` в тестах) остаётся сверка по `id` — она для него и так единственная.

**Не заменять хранение элементов на хранение одних `id`** ради экономии памяти: это и есть та
самая лотерея с переиспользованием адресов, от которой предостерегает комментарий.
