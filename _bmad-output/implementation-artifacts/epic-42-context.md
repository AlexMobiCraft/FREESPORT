# Epic 42 Context: Разделы админки для менеджеров, маркетинга и руководителя

<!-- Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. -->

## Goal

Сотрудникам нужен узкий набор действий, а сейчас его можно получить только вместе с полной Django-админкой, где лежат логи синхронизации, привязки к 1С и служебные поля. Флаг `is_staff` при этом открывает обмен с 1С и запуск импорта, а любой с правом `change_user` может поставить себе `is_superuser`. Эпик вводит три роли: «Менеджер», «Маркетинг» и «Руководитель». Каждая работает только в своём разделе с минимумом полей, а менеджер видит только клиентов своего региона. Основная `/admin/`, обмен 1С, запуск импорта и служебные метрики остаются за суперпользователем. Эпик готов, когда на стенде менеджер региона 23, маркетолог и руководитель проходят свои сценарии без доступа к `/admin/`, импорту и API обмена, а действия появляются в журнале. На проде готовность значит другое: у каждого клиента есть ответственный менеджер, а список нераспределённых регионов пуст. Требования не следуют из PRD и архитектуры, где о ролях сотрудников ничего нет. Они взяты из спецификации, согласованной с владельцем 08.10.2026; состав полей каждого раздела задан в `_bmad-output/specs/spec-staff-admin-sections/section-contents.md`.

- Story 42.3: Справочник регионов и разовый пересчёт ответственных
- Story 42.4: Раздел менеджера — клиенты своего региона
- Story 42.5: Раздел менеджера — заказы и главная страница

- Story 42.9: Журнал действий сотрудников

## Requirements & Constraints

- **Изоляция ролей.** Три группы с закреплёнными правами создаёт миграция, повторный прогон даёт тот же результат. Сотрудник любой роли получает отказ на `/admin/`, `/admin/monitoring/`, странице запуска импорта, API обмена 1С и API метрик синхронизации. Каталог с `include_inactive` не отдаёт ему неактивные товары. Доступ к служебному остаётся у суперпользователя и у владельца явного права: для обмена 1С это `integrations.can_exchange_1c`.
- **Нет пути эскалации.** Ни одна форма, доступная сотрудникам, не меняет `is_superuser`, `is_staff`, `groups` и `user_permissions`, в том числе при подделанном POST. Группу или право вне трёх ролей выдаёт только суперпользователь.
- **Фильтр по ответственному без обходов.** Он действует в списке, поиске, карточке по прямому URL, массовых действиях (включая подделанный список id), экспорте CSV, на страницах подтверждения B2B и смены пароля. На чужого клиента или чужой заказ раздел отвечает 404.
- **«Не показывать» значит «нет в HTML».** Служебные поля отсутствуют в форме и списке, а не становятся только для чтения. Подделанный POST их не меняет.
- **Сотрудники** (`is_staff`, `is_superuser`, члены трёх групп) не попадают в списки клиентов и не получают ответственного менеджера. Контрагенты 1С с ролью `unregistered` по умолчанию скрыты фильтром.
- **Журнал.** Каждое действие из перечня (верификация, отказ, блокировка и разблокировка, сброс пароля, смена роли, привязка к 1С, правка трек-номера, даты доставки или комментария, назначение и переназначение ответственного, правка правила региона, создание, блокировка и смена группы сотрудника) пишет ровно одну запись `AuditLog`. Действия, которые уже пишут запись, второй не создают.
- **Тесты.** У каждой проверки доступа есть негативный тест для каждой роли и каждого раздела, включая прямые URL карточек и служебных страниц. Проверки доступа — критический модуль с покрытием ≥ 90%, общее покрытие в CI ≥ 75%.
- **Производительность.** Число SQL-запросов на страницах списков (клиенты, заказы, товары, журнал) и в сводке не зависит от числа строк. Это проверяется тестом через `django_assert_max_num_queries`.
- **Обмен с 1С на проде не ломается.** Робот обмена ходит без `is_staff`, через `can_exchange_1c`, поэтому ветку `is_staff` из проверки обмена можно убирать без подготовки. Если меняются DRF-эндпоинты метрик, обновляется `docs/api/openapi.yaml` и должен проходить `check_openapi_sync`.
- Интерфейс, комментарии и docstrings пишутся на русском.

## Technical Decisions

- **Разделы — отдельные входы в Django-админке** (`/manager/`, `/marketing/`; руководитель видит оба и свой). Фронтенд Next.js не меняется. Сотрудникам нужен `is_staff=True` для входа, поэтому все проверки по `is_staff` в служебных местах заменяются проверкой суперпользователя или конкретного права.
- **Поля скрываются урезанными admin-представлениями.** Права Django действуют на уровне модели, одних групп недостаточно. Основная `/admin/` не перестраивается, из неё убирается только путь эскалации.
- **Существующая группа «Менеджер» на проде** (68 прав, один участник) переиспользуется: миграция переименовывает её в «Менеджеры» и заменяет набор прав. Второй группы рядом не появляется. Прямые права сотрудников миграция не трогает.
- **Регион клиента определяется одним правилом:** для страны вне России — по стране, иначе по первым двум цифрам `tax_id`, без ИНН — резервное правило. Определение делает существующий `resolve_manager_recipients`. Таблица `ManagerRoutingRule` — единственный источник и для видимости, и для писем о регистрации.
- **Правило региона ссылается на учётную запись менеджера.** Двух активных правил с одним кодом или одной страной быть не может, неактивный дубль допустим. Резервное правило указывает на руководителя. Миграция связывает старые правила с учётной записью по `manager_email`. Правило, для которого запись не нашлась, остаётся активным, и письма по нему идут на `manager_email`.
- **У клиента есть «Ответственный менеджер» и признак «назначен вручную».** Автоназначение срабатывает при регистрации, верификации, привязке к 1С, импорте контрагента и смене ИНН или страны. Ручное назначение эти события не перезаписывают. При смене менеджера в правиле клиенты региона без ручного назначения переходят к новому менеджеру.
- **Разовый пересчёт — management-команда, а не миграция** (4600+ контрагентов 1С). Она идемпотентна, умеет `--dry-run` и печатает отчёт: назначено по региону, ушло на резервное правило, пропущено из-за ручного назначения, без изменений.
- **Справочник регионов статичен:** коды 01–99, включая 90–95, а 99 — «Крупнейшие налогоплательщики». Неизвестный код выводится как есть.
- **Конфликты с 1С определяют, что только для чтения:**
  - статус заказа приходит только из 1С; ручной перевод в `accrual_status` начислил бы бонус сигналом `post_save`;
  - роль клиента назначается только на странице подтверждения B2B, а у связанного с 1С клиента её перезаписывает импорт;
  - описание товара перезаписывает импорт, поэтому маркетингу оно не даётся;
  - `discount_percent` — только подпись на бейдже, цену не меняет; маркетинг видит его только для чтения, действий со скидкой нет.
- **Заказы:** в списке только мастер-заказы, субзаказы показаны в карточке. Выручка в сводке считается по мастер-заказам без повторного сложения субзаказов. Гостевых заказов нет; заказы с пустым `Order.user` (наследие `order_export`) видит только руководитель.
- **Журнал построен на существующем `AuditLog`.** Лента показывает «дата — сотрудник — действие — объект» со ссылкой на объект и фильтрами по сотруднику и периоду. IP-адреса, User-Agent, сырого JSON и записей служебных операций (импорт, синхронизация) в ней нет.
- **Сводке нужна своя агрегация продаж в БД.** `CustomerSyncMonitor.get_business_metrics` считает метрики синхронизации и годится только как образец кэширования.
- **Ни одной роли не доступны:** сырые журналы аудита и синхронизации, `SyncConflict`, сессии импорта, мониторинг, все модели привязок к 1С, `OnecExcludedItem`, `PriceType`, `ColorMapping`, атрибуты, `ProductVariant`, дерево категорий каталога, `DeliveryMethod`, `Page`, `UserConsent`, `Cart`, `Favorite`, группы и права Django.
- **Процесс:**
  - перед правкой каждого символа — `npx gitnexus impact <symbol> --direction upstream -r "C:\Users\1\DEV\FREESPORT"`, отдельно обязательно по `Is1CExchangeUser` и `UserAdmin`;
  - перед коммитом — `detect-changes --scope all`;
  - тесты гоняются только в Docker, параллельные прогоны по одному compose-проекту запрещены.

## UX & Interaction Patterns

- Заголовок называет роль: «FREESPORT — Менеджер», «FREESPORT — Маркетинг», «FREESPORT — Руководитель».
- Главная раздела повторяет `backend/templates/admin/index.html` и `_app_block.html`, а счётчики стоят над списком моделей. У менеджера: «Заявки на верификацию: N, старейшая — X дней» и «Новые заказы: N» со ссылками на отфильтрованные списки. У маркетинга: «Подписчиков: N (+M за 30 дней)», без списка подписчиков.
- Отдельные страницы (подтверждение B2B, переназначение, сводка, журнал) сделаны по образцу `verify_b2b_view`: `admin_site.admin_view` плюс `each_context`.
- Массовое действие с вводом значения («Передать клиентов менеджеру») открывает промежуточную форму по образцу `merge_brands`.
- Метки товаров правятся прямо в списке (list_editable) и массовыми действиями «поставить/снять» для каждой метки.

## Cross-Story Dependencies

- Порядок: 42.1 → 42.2 → 42.3 → {42.4 → 42.5, 42.6} → 42.7 → {42.8, 42.9}. Ни одна стори не зависит от последующих, от других эпиков эпик не зависит.
- 42.1 — жёсткое предусловие всех остальных: пока `is_staff` открывает обмен 1С, выдавать учётные записи сотрудникам нельзя. 42.6 зависит только от 42.1 и может идти параллельно с ветвью менеджера.
- 42.4, 42.5, 42.7 и 42.8 опираются на поле ответственного из 42.2. Блок «Не распределены» в 42.7 берёт справочник из 42.3.
- 42.4, 42.5 и 42.7 сами пишут записи журнала о своих действиях. 42.9 строит ленту и тестом сверяет перечень действий целиком.
- **Точка выката на проде после 42.3.** Нужно завести учётные записи менеджеров, распределить регионы и вручную запустить пересчёт. Только после этого раздел менеджера (42.4) показывает клиентов.
- **Учётная запись `managermsk3@freesportopt.ru`** (id 15, `is_staff`, `role=admin`, 10 прямых прав) после 42.1 теряет доступ к `/admin/`. По решению владельца это руководитель. Сразу после выката 42.1 её вручную добавляют в «Руководители» и снимают прямые права. Своего раздела у неё не будет до выката 42.7.
