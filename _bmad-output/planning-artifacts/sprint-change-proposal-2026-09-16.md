## 3. Recommended Approach

### Выбранный путь

**Direct Adjustment** в рамках эпика 41: четыре стори, все решения владельца получены. Откат и пересмотр MVP не нужны.

### Рассмотренные варианты

| Вариант | Почему не выбран |
|---|---|
| Ничего не делать, приложить к отчёту обоснования | Длинные description, демо-страницы и `example` — реальные дефекты, не шум сканера |
| Одна большая стори «SEO по аудиту» | Смешивает каталог, auth-flow, гигиену маршрутов и юридические тексты: разные blast radius, разные ревьюеры |

### Оценка

| Стори | Объём | Слой | Решения |
|---|---|---|---|
| 41.17 | S–M | фронт | D1, D2 |
| 41.18 | M | фронт (middleware, auth-flow) | D3, D4 |
| 41.19 | S–M | фронт + конфигурация | D6, D7, D8 |
| 41.20 | S–M | фронт + бэк (реестр текстов) + docs | D5; E20 — решение владельца при create-story |

### Основные риски

- **41.18** касается пути входа. Регресс возврата после входа хуже любого замечания сканера, поэтому обязательна матрица сценариев (гость, авторизованный, прямой заход, старые ссылки `?next=`, открытие в новой вкладке, устаревшая cookie).
- **D4** — спорное SEO-решение. Эффект для Яндекса и Google нейтрален только при условии, что ни один адрес, закрытый `Disallow`, не должен быть в индексе, а индексируемые адреса `Disallow` не закрыты. Без теста инвариант со временем разойдётся.
- **D1** оставляет одну проваленную SEO-проверку («canonical на другой URL» у подборок). Это ожидаемо и не является регрессом.
- **H1/H2** по согласию на рассылку не проверяемы без сканера. Приёмка 41.20 не зависит от того, что покажет следующий отчёт.

### 5.2 Story 41.17: Метаданные подборок, короткий description категорий и поиск без URL-параметра

As a владелец магазина,
I want чтобы подборки каталога не дублировали его title и description, description категорий не обрезался в выдаче, а поиск из шапки не создавал отдельный адрес,
So that сканер и поисковик не находили дубли там, где страница отличается только фильтром.

**Закрывает:** FR-41-33. **Решения:** D1, D2.

**Контекст:**
- Механизм 41.13: серверная `generateMetadata` каталога (`(blue)/catalog/page.tsx`) валидирует `category` по `/api/v1/categories-tree/` и отдаёт canonical через `URLSearchParams`; без валидной категории — базовые метаданные `/catalog`.
- Подборки: `config/quickLinks.tsx` (`STATIC_QUICK_LINKS`: «Новинки», «Лидеры продаж», «Скидки»), `HitsSection.tsx:88` (`/catalog?is_hit=true`).
- Поиск из шапки: `components/layout/Header.tsx:122, 241, 300` → `/catalog?focusSearch=true`; автофокус — `CatalogPageClient.tsx:410, 1266-1273`, эффект зависит от `searchParams`.
- Базовый description `/catalog` (`catalog/page.tsx:10`) обещает «Оптовые и розничные цены» — уточняется до «Оптовые и рекомендованные розничные цены» (D2).
- Прод 16.09: 12 из 85 категорий имеют description длиннее 160 символов (максимум 173, «Форма для кикбоксинга и тайского бокса»).

**Тексты подборок (D1):**

| Адрес | title | description |
|---|---|---|
| `/catalog?is_new=true` | Новинки — каталог спортивных товаров \| OPTISPORT | Новинки в каталоге OPTISPORT: подборка спортивных товаров с ценами и условиями заказа для оптовых покупателей. |
| `/catalog?is_hit=true` | Лидеры продаж — каталог спортивных товаров \| OPTISPORT | Лидеры продаж в каталоге OPTISPORT: подборка спортивных товаров с ценами и условиями заказа для оптовых покупателей. |
| `/catalog?is_sale=true` | Скидки — каталог спортивных товаров \| OPTISPORT | Скидки в каталоге OPTISPORT: подборка спортивных товаров со сниженными ценами и условиями заказа для оптовых покупателей. |

Длины description — 110, 116, 121 символ.

**Acceptance Criteria:**

**Given** адрес `/catalog`, у которого единственный query-параметр — `is_new`, `is_hit` или `is_sale` со значением `true`
**When** строятся метаданные страницы
**Then** title и description равны таблице D1, canonical — `/catalog`, Open Graph и Twitter повторяют title и description, `keywords` нет (как у категорий 41.13)
**And** при любом другом наборе параметров (два флага, флаг вместе с `category`, `page`, сортировкой, значение не `true`) поведение 41.13 не меняется, а `sitemap.ts` подборок не содержит

**Given** каждая категория публичного дерева
**When** строится description по шаблону D2
**Then** длина не превышает 160 символов, слов «розничн…» нет, тест проверяет это на фикстуре с самым длинным именем
**And** title категорий, canonical и поведение для неизвестного slug не меняются

**Given** три ссылки на поиск в шапке (desktop, mobile, sticky)
**When** посетитель переходит по ним с любой страницы, в том числе уже находясь на `/catalog` (переход, меняющий только фрагмент адреса, не меняет `searchParams`)
**Then** `href` не содержит query-параметра, а поле поиска каталога получает фокус
**And** старый адрес `/catalog?focusSearch=true` из закладок по-прежнему фокусирует поиск, canonical у него `/catalog`

**Given** базовый `/catalog` и адреса категорий
**When** выполняются тесты стори 41.13
**Then** они проходят без изменения ожиданий, кроме description категорий по D2 и description базового `/catalog`
**And** description базового `/catalog` (`CATALOG_DESCRIPTION`, повторён в `catalog/__tests__/metadata.test.ts`) — «Каталог спортивных товаров: фитнес и атлетика, единоборства, спортивные игры, плавание, туризм. Оптовые и рекомендованные розничные цены, доставка по России.» (157 символов)

**Given** выкат на прод (NFR-41-08)
**When** `curl` с User-Agent `AuditikBot/1.0` запрашивает три подборки, две категории с самыми длинными именами и `/catalog?focusSearch=true`
**Then** у подборок title и description по таблице D1 и canonical `/catalog`, description категорий укладывается в 160 символов, у `focusSearch` метаданные базового `/catalog`; снимок приложен к стори

### 5.3 Story 41.18: Вход гостя без размножения адресов и один механизм исключения из индекса

As a владелец сайта,
I want чтобы служебные страницы входа, корзины и оформления не порождали дублей и противоречивых сигналов индексации,
So that отчёт показывал реальные проблемы, а не одну форму входа под четырьмя адресами.

**Закрывает:** FR-41-34. **Решения:** D3, D4.

**Контекст:**
- Источники `/login?next=…` в обходе гостя: ссылки `Header.tsx:131, 165, 249, 274, 308` и `Footer.tsx:50` на `/profile`, `/profile/favorites` → 307 в `middleware.ts:400-411` с `next=<pathname>`; `CheckoutStateView.tsx:11` (`/login?next=%2Fcheckout`).
- `Footer` — серверный компонент в `(blue)/layout.tsx`, состояния входа не знает. `Header` — клиентский. Ссылки обоих эта стори не меняет.
- Точка возврата после входа: `login/page.tsx:30` читает `next`/`redirect`, `LoginForm.tsx:62` проверяет `isSafeRedirectUrl` (`utils/urlUtils.ts`, укреплена в 41.12: backslash, origin, auth-route). Авторизованного на `/login` middleware отправляет на `next` (`middleware.ts:415-421`).
- Прод 16.09: `robots.txt` закрывает `/cart`, `/checkout`, `/profile`, `/search`, `/login`, `/register`, `/b2b-register`, `/password-reset`, `/portal-link`, `/coming-soon`, `/electric` и др. Meta `noindex` из этого списка стоит на `/cart`, `/checkout`, `/login` (`login/layout.tsx`), `/search`. Вне `Disallow` `noindex` стоит на `not-found.tsx`, `/unsubscribe` и по условию на `product/[slug]`, `blog/[slug]`, `news/[slug]`, `[slug]` — их стори не трогает.
