# Доказательная база: замеры прода и механизм отказа

Компаньон к `SPEC.md`. Числа — прод, срез 28.08.2026. Разбор механизма выполнен на паре сессий 66453 / 66454 и воспроизведён на 66628.

Учёт: `tech-debt.md` п. 26 («Каталог обмена 1С общий для всех сессий — изоляция отложена»). Предыдущая работа — стори `onec-import-cleanup-race-and-followups.md`, закрывшая удаление по glob-маске и тихий `COMPLETED` с нулём записей; структурная причина осталась и закрывается этой спекой.

## 1. Симптом

Сессия обмена падает с сообщением:

```
Файлы, присланные 1С этому прогону, не прочитаны
(rests_1_1_74a08eed-….xml — не найден в каталоге обмена):
данные не попали в БД, а 1С их не повторит.
```

Файл физически приезжал и был принят (`Перенесено файлов: 1/1`), но к моменту, когда задача получила доступ к каталогу, его там уже не было.

## 2. Замеры прода (окно 7 дней)

| Упавших сессий за 7 дней | 110 |

Корреляция полная: падает ровно то, что постояло в очереди.

| Тип сегмента | Падений |
|---|---|
| `rests` | 34 |
| `offers` | 18 |
| `goods` | 16 |
| `prices` | 15 |

**Цена вопроса.** Сегодня это в первую очередь недостоверный статус: в разобранных случаях файл успевал прочитать сосед, данные в БД попадали, но сессия отчитывалась провалом. Настоящая потеря выглядит **точно так же** — инцидент 25.08.2026: 6 сегментов остатков, ≈18 000 строк, 963 варианта торговались по старым данным. Пока падения идут пачками, отличить «файл прочитал сосед» от «файл не прочитал никто» можно только ручным разбором логов.

## 3. Механизм по шагам (66453 / 66454, 04:50 UTC)

| Время | Что произошло |
|---|---|
| 04:50:18.905 | Сессия **66453** создана по `mode=complete`, помечена `IN_PROGRESS`, задача ушла в Celery и **взяла лок каталога** |
| 04:50:20.954 | Сессия **66454** создана по `mode=import` с файлом `rests_1_1_74a08eed….xml` |
| 04:50:20.958 | Файл принят и положен в **общий** каталог `1c_import/rests/` |
| 04:50:20.961 | Задача 66454 ушла в Celery, но лок занят → `Каталог обмена занят другим импортом, задача отложена` |
| 04:50:21 | Держатель лока 66453 доходит до `Обновление остатков из rests.xml`, собирает по маске **все** `rests/rests*.xml` — включая только что приехавший чужой файл — читает его и удаляет как «свой обработанный» |
| 04:50:30 | 66454 получает лок, ищет обещанный ей файл — его нет → `CommandError` → **FAILED** |

Три условия, каждое по отдельности корректное:

1. **Каталог общий.** `FileRoutingService.import_dir = import_base` — без сегмента сессии.
2. **Чтение идёт по маске каталога, а не по обещанным именам.** `_collect_xml_files` собирает `prefix_*.xml` из подпапки типа, поэтому прогон забирает и чужие сегменты.
3. **Удаляется то, что прочитано.** `_cleanup_files` удаляет только реально распарсенные файлы и сверяет отпечаток — удаление **законно**: файл действительно был прочитан этим прогоном.

Гонка не в удалении. Она в том, что чужой файл вообще попал в чужой прогон.

## 4. Почему существующие guard-ы не закрывают

Их три, и все — проверка в один момент времени, после которой конкурент появляется.

| Guard | Где | Почему не спасает |
|---|---|---|
| Пропуск cleanup при активных сессиях | `views.py:427-453` (`handle_init`) | Проверяет `IN_PROGRESS` **до** старта; сессия-жертва создаётся через 2 секунды после |
| Пропуск post-import cleanup | `apps/products/tasks.py:486-506` | То же окно; к тому же файл убирает не он, а `_cleanup_files` |
| `defer_to_active_sessions` | `apps/products/tasks.py:414-423` | Считывается один раз на старте задачи. 66453 стартовала в 04:50:18, конкурент появился в 04:50:20 — на момент проверки его **не существовало** |

Классический TOCTOU на уровне сессий: между «посмотрел, кто активен» и «сгрёб каталог» проходят секунды, а 1С шлёт файлы каждые ~2 секунды.

## 5. Ключевой факт, определивший решение

**`session_key` уникален для каждого файла.** Замер: 85 сессий обмена за 20 минут → 85 разных ключей. 1С не держит cookie-сессию между запросами, каждый файл приходит как новый обмен. Следствия:

- изоляция вида `<import_dir>/<sessid>/<type>/` даёт **каждому файлу собственный каталог** — гонка исчезает структурно, а не по договорённости;
- **`mode=complete` при этом остаётся без работы**: своих файлов у него нет, чужие он больше не увидит. Сегодня 500 таких сессий в сутки сгребают каталог целиком и чаще всего оказываются держателем лока. Это не потеря функции — каждый файл уже импортируется собственной задачей;
- побочно закрывается мусор в `1c_temp` (32 276 пустых каталогов, по одному на сессию, никогда не удаляются).

## 6. Развилка и принятое решение

Изображения приезжают отдельными запросами от XML: архив с картинками и `goods.xml` — разные `sessid`. Сегодня они склеиваются в общем каталоге: XML ссылается на `import_files/<xx>/<file>.jpg`, и файл там лежит, потому что каталог один на всех. При полной изоляции склейка ломается.

| Вариант | Суть | Исход |
|---|---|---|
| **1** | Изолировать только XML-сегменты, `import_files` оставить общим | **Принят Alex 28.08.2026.** Все 85 падений — на XML; картинки складываются аддитивно, перезапись одноимённого файла безопасна. Минимальная правка, целевой эффект достигается |
| 2 | Изолировать всё, включая `import_files` | Отклонён. Требует связывать архив картинок с XML-сессией — механизма нет, 1С такой связи не передаёт. Дорого и хрупко |
| 3 | Не изолировать, а резервировать: файл переносится в `<import_dir>/.claimed/<session_pk>/`, `complete` берёт только незарезервированное | Отклонён. Эквивалентен варианту 1 по эффекту, но добавляет третью раскладку поверх существующих `temp` / `import` |

## 7. Что уже сделано и переделывать не нужно

- `_cleanup_files` больше **не** удаляет по glob-маске и сверяет отпечаток файла перед удалением — стори `onec-import-cleanup-race-and-followups.md`. Оставшийся там TOCTOU в доли миллисекунды — вне области этой работы.
- Тихий `COMPLETED` с нулём записей закрыт: `_assert_expected_file_processed` переводит такую сессию в `FAILED`. Именно поэтому дефект сегодня **виден** — до этого он прятался.
- Сессия, чей файл увёл сосед, больше не затирает свой отчёт при падении (`save(update_fields=…)`).
- `_bmad-output/race-condition-analysis.md` описывает ту же симптоматику, но причину образца Story 36.1 (пути `/app/media/1c_import`, обвинялся `handle_init`). Исторический контекст, работу по нему не переделывать.
