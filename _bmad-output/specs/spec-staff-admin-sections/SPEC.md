# Разделы админки для менеджеров, маркетинга и руководителя (эпик 42)

## Why

Боль и риск одновременно. Управлять клиентами и маркетингом сайта сейчас можно только через полную Django-админку. В ней рядом с нужным лежат логи синхронизации, привязки к 1С, служебные поля и настройки обмена. Сотруднику нужен узкий набор действий, а получает он всё. Выдать ему доступ безопасно нельзя:
- в карточке пользователя любой с правом «изменять пользователя» может поставить себе `is_superuser`;
- флаг `is_staff`, без которого в админку не войти, одновременно открывает обмен с 1С и запуск импорта.

Нужны три роли сотрудников. Каждая видит только свои разделы и минимум полей. Менеджер, кроме того, видит только клиентов своего региона.

## Capabilities

- **CAP-1** — роли сотрудников и изоляция
  - **intent:** Сотрудник с ролью «Менеджер», «Маркетинг» или «Руководитель» работает только в разделах своей роли. Основная админка, обмен с 1С, запуск импорта и служебные метрики ему недоступны.
  - **success:** Тест на каждую роль:
    - вход в разрешённый раздел — 200;
    - `/admin/`, страница запуска импорта, API обмена 1С и API метрик синхронизации — отказ.
    - сотрудник не может выдать себе или другому `is_superuser`, `is_staff`, группу или право вне трёх ролей ни через одну форму.

- **CAP-2** — регионы и ответственный менеджер
  - **intent:** Каждому клиенту назначен ответственный менеджер. Его определяет правило региона: страна, либо для России первые две цифры ИНН. Руководитель может назначить менеджера вручную, и ручное назначение пересчёт не затирает.
  - **success:** Тесты:
    - регистрация с ИНН `23…` назначает менеджера региона 23;
    - смена ИНН на `77…` переназначает клиента, если назначение не ручное, и не трогает ручное;
    - клиент без подходящего правила достаётся руководителю из резервного правила;
    - разовый пересчёт проставляет ответственного всем существующим клиентам;
    - письмо о регистрации уходит менеджеру из той же таблицы правил.

- **CAP-3** — раздел менеджера
  - **intent:** Менеджер ведёт клиентов, у которых ответственным указан он, и их заказы. Ему доступны:
    - верификация и отказ;
    - блокировка и разблокировка;
    - сброс пароля;
    - привязка к 1С.

    Служебных полей он не видит.
  - **success:** Менеджер региона 23:
    - видит в списке, поиске и экспорте только своих клиентов и их заказы;
    - по прямой ссылке на клиента или заказ другого менеджера получает 404, в том числе на страницах подтверждения B2B и смены пароля;
    - в карточке клиента не видит полей из блока «Не показывать» в `section-contents.md`;
    - каждое действие пишется в журнал (CAP-6).

- **CAP-4** — раздел маркетинга
  - **intent:** Маркетинг управляет:
    - баннерами, новостями, блогом и рубриками;
    - метками товаров;
    - брендами на главной;
    - категориями на главной.

    Кроме того, он видит число подписчиков. Ни данных клиентов, ни служебных полей товара он не видит, назначать скидку не может.
  - **success:** Маркетолог:
    - создаёт новость в новой рубрике;
    - массово ставит выбранным товарам метку «Хит» и снимает её;
    - видит на главной странице раздела число подписчиков.

    Списка подписчиков, клиентов, заказов, статических страниц и блока 1С в карточке товара у него нет: тест на отказ по прямым URL.

- **CAP-5** — раздел руководителя
  - **intent:** Руководитель видит разделы менеджера и маркетинга без фильтра по региону. Сверх того он:
    - управляет учётными записями сотрудников трёх ролей;
    - распределяет регионы;
    - переназначает клиентов;
    - видит сводку;
    - настраивает получателей уведомлений и бонусную программу.
  - **success:** Руководитель:
    - создаёт менеджера;
    - назначает ему регион 23 и видит, что код 23 пропал из списка нераспределённых;
    - массово передаёт всех клиентов менеджера A менеджеру B, после чего B сразу видит их, а A нет.

    Создать суперпользователя или отредактировать другого руководителя руководитель не может (тест на отказ).

- **CAP-6** — журнал действий сотрудников
  - **intent:** Руководитель видит понятную ленту действий сотрудников: «кто, когда, что сделал с каким клиентом или заказом», с фильтром по сотруднику.
  - **success:** Каждое действие из перечня журнала в `section-contents.md` появляется в ленте с автором, временем и объектом. Фильтр по сотруднику оставляет только его записи. Технических полей (IP-адрес, User-Agent, JSON) в ленте нет.

## Constraints

- **`is_staff` открывает слишком много.** Сегодня он даёт доступ к:
  - обмену 1С: `Is1CExchangeUser`, `onec_exchange/permissions.py:11`;
  - странице запуска импорта: `staff_member_required`, `integrations/views.py:29`;
  - метрикам синхронизации: `IsAdminUser`, `common/views.py:146-310`;
  - неактивным товарам каталога: `products/views.py:515`.

  Роли сотрудников этот доступ наследовать не должны. Проверки на `is_staff` в этих местах заменяются проверкой суперпользователя или конкретного права.
- **Эскалация через форму пользователя.** `UserAdmin` отдаёт в форму `is_superuser`, `is_staff`, `groups` и `user_permissions` любому с правом `change_user`. Ни одна форма, доступная ролям сотрудников, этих полей содержать не должна. Основная `/admin/` — только для суперпользователя.
- **Скрытие полей.** Права Django работают на уровне модели. Скрыть поля 1С и служебные поля внутри карточки можно только отдельными урезанными представлениями, одних групп недостаточно.
- **Фильтр по региону действует везде:** в списке, поиске, карточке по прямому URL, массовых действиях, экспорте CSV, на страницах подтверждения B2B и смены пароля. Обхода по ссылке быть не должно.
- **Регион клиента определяется так же, как в `region_routing.resolve_manager_recipients`:** страна вне России — по стране, иначе по первым двум цифрам `tax_id`. Таблица `ManagerRoutingRule` остаётся единственным источником и для видимости, и для писем о регистрации.
- **Описание товара маркетингу не даётся.** Импорт 1С перезаписывает его непустым значением из выгрузки (`variant_import.py:1178`).
- **Роль клиента назначается только при верификации**, на странице подтверждения B2B. В карточке клиента роль только для чтения. У клиента, связанного с 1С, её затем перезаписывает импорт по виду цен соглашения (`users/services/processor.py:618`). Решение Alex 08.10.2026.
- **Статус заказа приходит только из 1С** (`order_status_import.py:755`, `:899`), в разделах сотрудников он только для чтения. Ручной перевод в `BonusProgramSettings.accrual_status` начислил бы бонус тренеру сигналом `post_save` (`bonuses/signals.py:18`), а импорт затем перезаписал бы статус. Решение Alex 08.10.2026.
- **На регион назначен ровно один ответственный менеджер** (решение Alex 08.10.2026). Таблица правил не допускает двух активных правил с одним и тем же кодом региона или страной.
- **Гостевых заказов нет:** создание заказа требует авторизации (`orders/views.py:37`). `Order.user` допускает пустое значение только как наследие `order_export`. Заказы без клиента, если найдутся, видит только руководитель.
- **Учётные записи сотрудников** (`is_staff`, `is_superuser`, члены трёх групп) в списки клиентов не попадают и ответственного менеджера не получают.
- **Журнал строится на существующем `AuditLog`.** Действия, которые уже пишут запись (`block_user`, `change_password`, верификация), не дублируются отдельным механизмом.
- **Только Docker и PostgreSQL.** Тесты — `cd docker && docker compose -p freesport-test -f docker-compose.test.yml run --rm -T backend pytest …`. Параллельные прогоны по одному compose-проекту запрещены.
- **GitNexus обязателен:** `impact --direction upstream` до правки каждого символа, `detect-changes --scope all` перед коммитом, только CLI с `-r "C:\Users\1\DEV\FREESPORT"`.
- **Язык:** интерфейс, комментарии и docstrings — на русском.

## Non-goals

- Сверка ответственного менеджера с ответственным менеджером партнёра в 1С и доработка выгрузки БУС под неё (отложено, решение Alex 08.10.2026).
- Статические страницы (`Page`) в разделе маркетинга.
- Список и экспорт подписчиков для маркетинга.
- Отдельное «маркетинговое описание» товара.
- Назначение скидки (`discount_percent`) в разделе маркетинга: поле только подпись на бейдже и цену не меняет (решение Alex 08.10.2026).
- Просмотр менеджером клиентов чужого региона, даже только на чтение.
- Отдельная очередь «Без менеджера»: её роль выполняет резервное правило на руководителя.
- Перестройка основной `/admin/` для суперпользователя. Из неё убирается только путь эскалации, остальное остаётся как есть.
- Изменения во фронтенде Next.js: все разделы живут в Django.
- Разбор дублей `tax_id` (65 групп на проде).

## Success signal

На стенде заведены менеджер региона 23, маркетолог и руководитель. Каждый проходит свой сценарий из CAP-3, CAP-4 и CAP-5 и не может открыть ни `/admin/`, ни запуск импорта, ни API обмена 1С. Руководитель передаёт клиентов от одного менеджера другому, и это сразу видно в обоих разделах, а все действия сценариев появляются в журнале. На проде после выката у каждого клиента есть ответственный менеджер, а список нераспределённых кодов регионов пуст.

## Assumptions

- Каждый раздел — отдельный вход в Django-админке (`/manager/`, `/marketing/`). Руководитель видит оба и свои пункты. Сотрудникам нужен `is_staff=True`, чтобы войти в Django-админку.
- Названия регионов берутся из статического справочника кодов 01–99 по первым цифрам ИНН, включая 90–95 и 99 (крупнейшие налогоплательщики).
- Разовый пересчёт ответственного охватывает и контрагентов 1С без портального аккаунта (`role=unregistered`). Менеджер видит их через фильтр, по умолчанию они скрыты.
