# Письма о новом заказе: доставка и получатели региона

## Why

Боль. Менеджеры и руководитель не узнают о заказах с сайта, а клиент не получает подтверждение. Причин две. Задачи отправки ставятся в очередь до фиксации транзакции и не находят заказ: на проде по заказу `0000226001` (30.10.2026) обе задачи вернули `False` через 23 и 41 мс после создания мастера, без повтора и без следа в БД. Кроме того, письмо о заказе получает только один адрес из `NotificationRecipient`: руководитель выключен, менеджеров в списке нет. Заказ клиента регионального менеджера может пролежать незамеченным, пока менеджер сам не заглянет на сайт.

## Capabilities

- **CAP-1** — письма только после фиксации заказа
  - **intent:** Письма клиенту и получателям ставятся в очередь только после того, как заказ с субзаказами и позициями зафиксирован в БД.
  - **success:** Тест через `OrderCreateService`: до коммита задачи не поставлены, после коммита каждая поставлена один раз и находит заказ со всеми позициями. При откате транзакции задачи не ставятся. Для субзаказа не ставятся.

- **CAP-2** — заказ не зависит от очереди
  - **intent:** Недоступный или зависший брокер после фиксации не ломает оформление заказа и не держит запрос дольше таймаута gunicorn, а сбой остаётся в логе с номером заказа.
  - **success:**
    - Тест: `.delay` бросает исключение; блок захвата колбэков завершается без исключения, `POST` создания заказа отвечает 201, заказ есть в БД, вторая задача всё равно поставлена, в `caplog` есть номер заказа. Сам по себе ответ 201 здесь ничего не доказывает: при `ATOMIC_REQUESTS=True` в тестах колбэки срабатывают уже после ответа.
    - Тест: `.delay` приложения с настройками проекта к сокету, который принял соединение и молчит, заканчивается исключением быстрее 15 с.
    - Проверка на dev-стеке: воркер с новыми настройками простаивает без переподключений и после перезапуска Redis снова забирает задачи.

- **CAP-3** — письмо ответственному менеджеру клиента
  - **intent:** Ответственный менеджер клиента, оформившего заказ, получает письмо о каждом его новом заказе со ссылкой, которая у него открывается.
  - **success:** Тесты задачи `send_order_notification_email`:
    - менеджер клиента получает письмо со ссылкой на `/manager/`, менеджер другого региона не получает;
    - при ручном назначении письмо получает назначенный вручную, а не менеджер правила региона;
    - письмо уходит менеджеру и при пустом общем списке, задача возвращает `True`;
    - адрес, который есть и в общем списке, и у менеджера, получает одно письмо, регистр email не важен;
    - ответственный заблокирован, выведен из групп, не задан или у заказа нет клиента: письмо уходит общему списку, задача не падает, для заказа с клиентом в логе предупреждение с номером заказа в тексте сообщения.

- **CAP-4** — письмо руководителю
  - **intent:** Руководитель получает письмо о каждом новом заказе. Флаг в его разделе выключает только общий список: по своим клиентам письмо приходит, как любому ответственному.
  - **success:**
    - Запись `managermsk3@freesportopt.ru` на проде имеет `notify_new_orders=true`; в письме ссылка на `/manager/`, заказ по ней открывается (тест на запись с группой «Руководители»).
    - Тест: при `notify_new_orders=false` ответственный руководитель получает письмо о заказе своего клиента и не получает о заказе чужого.
    - Форма записи в разделе руководителя показывает у флага подсказку: выключение действует только на общий список.

## Constraints

- Единственный источник менеджера клиента — `User.responsible_manager`. Новую логику региона не вводить: поле уже считается из `ManagerRoutingRule` и учитывает ручное назначение.
- Менеджер видит в `/manager/` только заказы клиентов, у которых он ответственный (`scope_clients`), поэтому письмо с резервного правила другому менеджеру дало бы ссылку, которая не открывается.
- `NotificationRecipient` остаётся единственным механизмом общего списка получателей. Флаг `notify_new_orders` управляет только этим списком; ответственный менеджер добавляется к письму независимо от него: значение по умолчанию `False`, поэтому `False` не означает отказа.
- Таймауты и лимиты повторов Celery задаются одним местом, в `settings/base.py`, для всех задач: без параметров в отдельных вызовах и своих обёрток вокруг `.delay`.
- Колбэк `on_commit` с `robust=True` — `lambda` или именованная функция, не `functools.partial`: Django читает `__qualname__` колбэка в обработчике ошибки, и у `partial` упадёт сам обработчик.
- На проде заказ уходит в рабочую 1С: контрольные заказы для проверки на проде не создавать.
- Изменения данных прода — только с подтверждения владельца, правка одной записи `common_notificationrecipient`.

## Non-goals

- Отправка писем задним числом по заказам `0000126001` и `0000226001`.
- Гарантированная доставка: outbox, журнал отправленных писем, повтор после исчерпания попыток Celery.
- Новый текст и оформление письма, отдельный шаблон для менеджера.
- Привязка руководителя к региону, письма нескольким менеджерам одного клиента.
- Письма об отмене заказа и прочие уведомления.
- Обратный канал из 1С и подтверждение создания документа там.
- Изменение состава общего списка, кроме флага руководителя.
- Таймауты кэша Redis (`django-redis`). Они управляют поведением всего сайта при сбое Redis, а не письмами о заказах.

## Success signal

Следующий реальный заказ любого клиента после релиза: письмо `[OPTISPORT] Новый заказ #…` получили ответственный менеджер этого клиента, `managermsk3@freesportopt.ru` и `alexmw2006@gmail.com`, подтверждение — клиент, а ссылка из письма открывает заказ у менеджера и руководителя. Наличие письма спросить у получателей; результаты Celery в Redis смотреть, только если заказ пришёл меньше суток назад.

## Assumptions

- Руководитель в группе «Руководители» один. Общий список к региону не привязан, поэтому руководитель получает все заказы.
- `managermsk3@freesportopt.ru` — менеджер резервного правила и ответственный за 506 клиентов (31.10.2026). Письма по этим клиентам приходят с первого заказа после релиза, ещё до включения флага.
- Письма по заказам `0000126001` и `0000226001` не отправляются: менеджеры предупреждаются вручную.
- Если Redis перезапускается в момент оформления, задача не ждёт его 19 с, как сейчас, а сразу пишет сбой в лог: письмо по этому заказу не уйдёт. Это допустимо: гарантированная доставка вне этой спеки.
- Если вторая отправка в задаче упала и задача повторилась, первая группа получит дубль. Дубль допустим, потеря нет.
