# План резервной доставки образов из CI по SSH

Статус: проект на согласование. Ничего из описанного ещё не внедрено.

## Задача и границы

В двух попытках [прогона №45378114937](https://github.com/AlexMobiCraft/FREESPORT/actions/runs/45378114937) Docker на проде получал `unexpected EOF` при загрузке frontend из GHCR, а job исчерпал 30-минутный лимит до переключения контейнеров. Когда те же образы заранее появились на сервере, [штатная выкатка](https://github.com/AlexMobiCraft/FREESPORT/actions/runs/45413604047) заняла 1 мин 50 с. Точная точка сетевого обрыва не установлена.

Добавляем резервный маршрут **GHCR → раннер GitHub Actions → прод по SSH**. Раннер доставляет уже опубликованные CI образы, не пересобирая их. Прод остаётся зависим от GitHub для `git fetch` исходников и конфигурации, но не скачивает образы приложения из GHCR в резервном режиме. Это не решение для полной недоступности GitHub.

Не меняем Dockerfile, размеры образов, правила `develop → main`, ручное подтверждение `production` и действующий порядок применения миграций. Сборка на проде или рабочем ПК, постоянный PAT, новый туннель и автоматическое переключение на резервный маршрут не входят в первую версию.

## Как оператор будет запускать

В [`deploy.yml`](../../.github/workflows/deploy.yml) добавить ручной параметр `delivery_mode`:

| Значение | Поведение |
| --- | --- |
| `registry` | По умолчанию. Обычный push в `main` и текущий ручной деплой сохраняют загрузку с GHCR на сервере. |
| `ssh` | Только `workflow_dispatch` для `production` из `main`. Требует `image_tag` уже собранного текущего релиза; использует готовые образы без сборки. |

Пример для будущего запуска: `gh workflow run deploy.yml --ref main -f environment=production -f delivery_mode=ssh -f image_tag=<SHA-тег>`. После этого оператор подтверждает `production` в GitHub Actions. Обычная группа `concurrency` остаётся общей для обоих режимов.

В первой версии `ssh` не используется для выката старого SHA, если `main` уже ушёл вперёд. Сейчас штатный скрипт берёт конфигурацию с `origin/main` даже при указании старого тега; не расширяем этот сценарий, пока нет отдельного решения о связке исходников, конфигурации и образов для отката. Действующий режим отката через `registry` сохраняется.

## План реализации

### 1. Проверить выбранный релиз на раннере

- В `setup` проверять допустимый режим и формат SHA-тега, отклонять `ssh` без явного тега, вне `main` или не для `production`. Не подставлять пользовательский ввод прямо в shell-код; передавать через переменные окружения.
- После ручного подтверждения раннер авторизуется в GHCR через `GITHUB_TOKEN` с `packages: read`. Токен не передаётся на прод в режиме `ssh`. Проверить, что оба пакета дают workflow доступ на чтение и настройка разрешений не ломает текущий job уведомлений.
- Получить из GHCR digest, соответствующий SHA-тегу, отдельно для backend и frontend. Скачать оба образа по digest для `linux/amd64` и сверить полный `org.opencontainers.image.revision` с `github.sha`. Сохранить в манифест доставки пару digest из GHCR, Docker image ID каждого образа, полный SHA коммита и контрольные суммы архивов. SHA-тег выбирает релиз; digest фиксирует содержимое, скачанное раннером.

### 2. Передать и проверить архивы без переключения

- Экспортировать образы через `docker save` и сжать `zstd`, используя временные теги, привязанные к проверенным image ID. Не назначать `:production` при импорте. До передачи проверить наличие инструментов и свободное место на раннере и в хранилищах архива и Docker на сервере.
- Передавать через `rsync` поверх SSH с `--partial-dir` и ограниченным числом повторов для одного и того же файла. Не использовать поток `ssh ... docker load`: при обрыве его пришлось бы передавать заново. В первой версии докачка гарантируется в пределах одного прогона; между разными прогонами она не обещается. Ключ хоста сверять с заранее подтверждённой записью `known_hosts`, а не доверять одному `ssh-keyscan`.
- Хранить файлы во временном каталоге вне рабочей копии, с доступом только у пользователя деплоя и уникальным путём на прогон. Сверить SHA-256 архивов до `docker load`; после импорта проверить image ID, платформу и полный SHA у каждого образа. Не требовать, чтобы `docker load` восстановил реестровый `RepoDigest`: привязку к нему проверяем на раннере, а на сервере сверяем image ID из манифеста.
- Ограничить время и объём хранения частичных файлов. После прогона удалять только файлы его каталога; для отменённых прогонов предусмотреть уборку просроченных каталогов с проверкой, что они уже не используются. В сводке прогона показать этап, объём, время и число повторов без вывода секретов.

### 3. Включить штатное переключение только после проверки пары образов

- Разделить подготовку образов и переключение на отдельные шаги в `deploy-production`, сохранив одно подтверждение. У передачи будет собственный лимит, у переключения и проверок — свои. Стартовые ориентиры: до 45 минут на SSH-подготовку и до 15 минут на переключение; общий лимит job должен учитывать также checkout, бэкап и проверки. Уточнить цифры по тестовой передаче; не давать переключению автоматически унаследовать лимит транспорта.
- В `ssh` до успешной проверки обоих образов не менять рабочую копию, контейнеры или схему БД. Перед переключением сверить свежий `origin/main` с SHA подготовленной пары; если `main` успел измениться, завершить прогон без выката. Точку возврата снять с реально работающих контейнеров до замены; не брать её из тегов доставленных образов.
- После подготовки использовать общий проверенный сценарий: бэкап БД, обновление рабочей копии, Compose, миграции, статика, nginx и внешние проверки. В `ssh` запускать сервисы приложения без возможности скачивания образов (`--pull never`), используя ссылки на проверенные локальные образы. Не дублировать сценарий переключения и не делать автоматический откат при сбое передачи: контейнеры в этом случае не менялись.
- Различать в диагностике сбой доставки до переключения и сбой после начала переключения, включая отмену по таймауту. В первом случае выводить инструкцию повторить доставку; во втором — ссылку на бэкап и сохранённые образы. Не считать обратный запуск образов автоматическим откатом миграций.

## Проверка и ввод в эксплуатацию

| Сценарий | Ожидаемый результат |
| --- | --- |
| Обычный push в `main` и текущий `workflow_dispatch` без `delivery_mode` | Идут по `registry`; процесс подтверждения не меняется. |
| `ssh` без тега, с неподходящим SHA или из другой ветки | Прогон останавливается без выката. |
| Тестовая передача штатных образов в изолированный Docker | У обоих образов проверены платформа и SHA; image ID на получателе совпадают с оригиналами; для запуска приложения не нужен GHCR. |
| Прерванная передача, испорченный архив, второй образ отсутствует или не хватает места | Повтор передачи продолжает загрузку того же файла; при неисправимой ошибке переключение не начинается. |
| `main` изменился во время передачи, таймаут или отмена до переключения | Рабочая копия и запущенные контейнеры не изменились; в логах понятно, где прервался прогон и что повторить. |

Сначала проверить синтаксис workflow и прогнать перенос без запуска контейнеров на тестовой машине или в изолированном Docker. Затем по отдельному согласованию проверить доставку на прод без переключения. Первый реальный `ssh`-деплой провести для заранее выбранного релиза после ручного подтверждения: сверить фактические image ID работающих backend, frontend и Celery, проверить миграции и внешний health check. После этого добавить краткую инструкцию выбора режима в runbook.

Критерий готовности: если прод не может скачать образы приложения из GHCR, оператор запускает резервный режим без PAT и локальной сборки; прод переключается только после доставки и проверки обоих исходных образов CI.
